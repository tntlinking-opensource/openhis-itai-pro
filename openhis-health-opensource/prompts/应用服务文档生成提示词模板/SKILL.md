# 应用服务文档生成提示词模板（AS）

## 1. 适用范围

- 目标：为**单一页面/场景**产出「应用服务设计（AS）」文档，作为上游业务契约与编排权威。**默认一个页面对应一份 AS；复杂页面（如医生站含多个独立功能模块）若功能边界清晰，可按模块拆分为多份 AS**。
- 交付：仅产出 1 份 Markdown，落盘 `docs/应用/zxplat-application/AppService/`。
- **触发**：用户要求写/补 AS，或 @ 本 Skill；**禁止**在纯改码/改库/改 UI 会话中主动新建 AS。
- 命名：`AS-{域}-{子域}-{序号}-{场景名}.md`。
- 原则：章节结构以本 SKILL 为唯一基线，不依赖外部模板文件。

> **多域编排限定**：应用层（AS）**可编排多域聚合**。一个页面的按钮操作可能涉及多个域的聚合（如门诊医生站的「办理住院」涉及 Encounter 域与 EpisodeOfCare 域的多域编排），AS 文档应如实列出所有涉及的域，不得因"这不是本域的事"而删减 IF 或缩小边界。领域层（DM）的聚合边界不等于应用层编排边界。

## 2. 输入权威与优先级

1. 用户当期任务说明与评审裁决（最高）。
2. **当前 UI 设计与交互契约（`zxplat-ui/apps` 与新版 UI）**：**决定接口列表**——提取所有按钮/菜单/操作映射为 IF；禁止从 DM 反向推导 UI 功能。**同一后端能力的多个触发入口（如列表查询的切队列/关键字/日期/刷新）合并为一个 IF，不按 UI 输入项逐一拆分**。
3. **初版后台源码（`openhis-sever/openhis-application`）**：**业务编排唯一真源**——状态流转、校验规则、编排步骤、异常口径**必须照搬老代码业务逻辑**；**老代码分工可能分散在各模块（如退费逻辑在收费模块、处方逻辑在药房模块），AS 需跨模块查找并吸收业务规则，不关心老代码原有分工，只确保业务逻辑正确性**；禁止 AI 自行编排或脑补业务逻辑。
4. **DomainModel（DM）文档**：**领域能力基础设施**——提供老代码业务编排所依赖的聚合方法、状态机、领域事件、不变式；DM 是能力的「供应商」，老代码是能力的「消费者」；AS 可编排多域聚合（调用多个域的 DM 能力）。
5. **DM §6.2（*QueryService）**：**读侧能力基础设施**——提供老代码查询逻辑所依赖的 QueryService 方法、QueryModel 与组装规则。
6. 同场景已正式发布或以评审确认为准的 AS 文稿。

冲突处理：
- **UI 有但老代码无**：UI 设计了某按钮但老代码无对应业务逻辑 → 询问用户该按钮的业务规则；若编排依赖**领域写侧**尚不存在的方法/事件/状态迁移，入 **DM 能力** Gap（见 §5.3）；**不得**因「应用层 AppService/Controller 未实现」入 Gap。
- **老代码有但 UI 无**：老代码有某业务编排但 UI 未设计对应按钮 → 入 §1.4「非目标」写明舍弃。
- **老代码业务编排 vs DM 能力不匹配**：老代码编排依赖的某方法/状态在 DM 中不存在 → 入 **DM 能力** Gap（具体到 DM 文件及章节缺什么方法/事件）；DM 有但老代码未使用的能力 → 不额外引入，维持老代码现状。
- 用户说明 vs DM：以用户当期裁决为准。

> **AS 文档跟随 UI 页面（默认）**：一个页面对应一份 AS 文档，UI 上所有按钮/操作都必须有对应 IF。**例外：复杂页面功能模块边界清晰时（如医生站含就诊管理、费用管理、处方管理等独立模块），可按功能模块拆分多份 AS，每份聚焦特定业务能力**。

## 3. AS 文档职责边界（硬门禁）

**AS 是页面级契约文档（默认）**：一个 UI 页面对应一份 AS 文档，该页面所有可交互元素（按钮、菜单、操作）都必须映射为 IF。**复杂页面功能模块边界清晰时（如医生站），可按模块拆分，每份 AS 只映射本模块的交互元素**。

AS 必须写：
- 场景边界、业务目标、角色与范围（明确**涉及域**：本页面编排涉及哪些域的聚合）。
- IF 清单（接口 ID 稳定）、业务语义、**涉及领域（可多域）**、查询服务；**本 AS 范围内的按钮写 IF，不属于本 AS 功能模块的按钮不写**（应在其他 AS 文档收敛）。
- 业务规则（BR）与异常口径。
- 按 IF 的业务编排意图（自然语言级）。
- 非功能要求与缺口跟踪。
- 覆盖声明：完整覆盖初版后台同场景业务能力，并按当前 UI 设计组织接口。

AS 禁止写：
- 代码包路径、依赖注入清单、领域方法白名单。
- Request/Response 字段级明细。
- 伪代码、写库顺序、事务提交点细节。
- QueryService 字段组装规则、测试实现步骤。
- 来源暴露语句（正文不得写"来源于 openhis-sever/zxplat-ui/初版代码"等）。

> 上述内容属于 SDD 职责。AS 是"做什么 + 为什么"，不是"怎么写代码"。
> 
> **功能模块拆分示例**：医生站为复杂页面，按功能模块拆分为多份 AS：
> - **AS-OP-DOR-001 就诊管理**：就诊列表、接诊、暂离、完诊、办理住院（就诊生命周期及流转）
> - **AS-OP-DOR-00x 费用管理**：退费、划价（收费域逻辑）
> - **AS-OP-DOR-00x 处方管理**：处方单、处方查询（处方域逻辑）
> 
> 判断标准：功能模块是否围绕同一业务能力（如就诊生命周期）还是独立业务（如收费、处方）。同一页面的按钮可能分属不同 AS。

## 4. 固定章节骨架（必须逐字同构）

> 生成时必须使用以下主章节与顺序；不得删章、并章、改名。

1. `## 1. 场景概述`
2. `## 2. 页面与接口总览（契约概览）`
3. `## 3. 缺口跟踪（Gap）`
4. `## 4. 接口编排说明书（业务步骤）`
5. `## 5. 业务异常与用户提示`
6. `## 6. 事件语义与消费方`
7. `## 7. 非功能性需求`
8. `## 8. 测试要点（业务视角）`
9. `## 9. 关联文档与变更历史`

## 5. 各章最小深度

### 5.1 `## 1. 场景概述`

必须包含：
- `### 1.1 目标与边界`（在内/在外/涉及域）
- `### 1.2 角色与关键动作`
- `### 1.3 术语与口径约定`
- `### 1.4 本期范围与非目标`
- `### 1.5 领域清单（聚合 + 职责 + DM 路径）`
- `### 1.6 业务规则（BR-*）`

### 5.2 `## 2. 页面与接口总览（契约概览）`

必须给出 IF 总表，列至少包含：
- IF 编号
- 用户动作
- 接口语义
- 读/写属性
- 关键规则（BR 引用）
- 关键状态变化（自然语言）
- 涉及领域
- 查询服务（*QueryService）

### 5.3 `## 3. 缺口跟踪（Gap）`

> **Gap 唯一落点**：**仅 AS 文档 §3** 可写 Gap。**SDD 禁止出现 Gap 章节、Gap 表或「待实现应用层」类表述**——应用层由 SDD 驱动生成，缺 AppService/Controller/DTO/Mapper **不是** Gap。

**Gap 语义（硬定义，违反即 FAIL）**：

Gap **只表达「领域层（含 QueryService）尚不具备 AS 编排所需能力，或领域层文档与领域层代码不一致」**。可验收对象为以下三类之一，**禁止第四类**：

| 缺口类型 | 表达什么 | 可验收关闭条件（示例） |
|----------|----------|------------------------|
| **QueryService 能力** | DM **§6.2 未就绪**（缺 AS 编排所需的 `*QueryService#method` 签名或实现） | DM §6.2 补齐方法；领域代码实现并与文档一致 |
| **DM 能力** | DM `§6`（或等价「领域服务方法」章）**无** AS 编排序列所需的**写侧** `*DomainService#method(Command)`、状态迁移或领域事件 | DM 增补方法签名 + 事件；**领域代码**实现该方法 |
| **代码-文档不一致** | **仅限领域层**：DM/DM §6.2 查询契约与 `zxplat-domain` / `zxplat-domain` / QueryService 实现**已存在代码**矛盾 | 以评审裁决为准，补文档或改领域代码，两侧一致 |

**不属于 Gap（写进表即 FAIL）**：

| 禁止项 | 正确处置 |
|--------|----------|
| 应用层未实现（无 `*AppService`、无 Controller 路由、无 Request/DTO/Mapper） | **正常**：由 SDD → 应用层代码生成解决，**不得**入 Gap |
| AS/SDD 未编写、SDD 草稿不全 | 流程问题，**不得**入 Gap |
| 前端/UI/产品未定 | §1.4 非目标或项目外跟踪，**不得**入 Gap |
| 编排需「新增 IF」但属应用层拼装 | 修订 AS/SDD，**不得**入 Gap |
| DM §6.2 查询契约**已有**、仅 App 层 DTO 字段组合不同 | 在 SDD §3 字段表解决，**不得**入 Gap |
| QueryService 刷新延迟、最终一致、性能调优 | §6/§7 语义，**不得**入 Gap |
| 「建议补充 xxx」「待确认」「可能缺」等不可验收表述 | **禁止**入表 |

必须显式列：
- Gap ID、**缺口类型**（上表三选一）、**文件 + 章节**、**缺什么 / 不一致点**、**关闭条件**、影响 IF、优先级、状态。
- 若无**合格**领域层缺口，写「**无待跟踪缺口**」（可单行表或固定句式），不得留空。

**Gap 表格列（强制，按列填写，不得合并或改名）**：

| Gap ID | 缺口类型 | 文件 + 章节 | 缺什么 / 不一致点 | 关闭条件 | 影响 IF | 优先级 | 状态 |
|--------|----------|-------------|-------------------|----------|---------|--------|------|

- **文件 + 章节**：**仅** `DM-*.md`、`DM §6.2`、`领域事件处理（已废止）-*.md` 或领域层 Java（`zxplat-domain` / queryservice 包（已删除））路径；**禁止**写 `AppService-SDD`、`*AppService.java`、`*Controller` 作为 Gap 落点。
- **缺什么 / 不一致点**：必须指向 **领域服务方法名 / QueryService 方法名 / 领域事件名 / 状态机迁移** 或 **DM 字段与领域实体字段不一致**；禁止「缺接口实现」「待开发后端」。
- **关闭条件**：必须可验收为 **DM 或DM §6.2 查询契约已补齐** 且 **领域层代码已实现或文档已改与代码一致**；禁止「应用层联调通过」作为唯一关闭条件。
- 三列合计不超过两行；禁止在表格单元格内写多段文字或换行块

### 5.4 `## 4. 接口编排说明书（业务步骤）`

按 IF 分节，必须包含：
- 触发前提
- 主路径步骤（业务语言）
- 关键分支
- 失败分支
- 查询侧说明（语义级）

禁止出现代码级方法名、伪代码或字段表。

**推荐呈现**：每个 IF 使用「维度表」表达上述五项（与仓库内已对齐范例 `AppService/AS-OP-FIN-001-门诊挂号.md` 等一致）。若场景强依赖先后次序，可在同小节内增加简短顺序列表辅助阅读，但仍不得出现代码级方法名或字段明细。

### 5.4.1 IF 编号纪律（门禁）

- **§2 契约母表**为全文 IF 真源：§4、§6 触发相位、BR/Gap 引用须与之完全一致。
- **合并或废弃**某一 IF 时，须同步全文改号并更新 BR、Gap、§4、§6，不得长期保留「（已合并）占位 IF」造成序号空洞或与正文脱节。

### 5.5 `## 5~8`

- §5：异常场景、用户提示语义、是否可重试。
- §6：事件名、触发点、消费方、幂等等语义（不写字段映射）。
- §7：性能、幂等、并发、一致性、审计等业务侧承诺。
- §8：业务测试要点（正向/异常/规则/并发），不写具体测试代码。

### 5.6 `## 9`

- 关联文档：DM、DM §6.2、上下游 AS（路径可追溯）。
- 变更历史：版本、日期、变更摘要。

## 6. 生成流程（强制顺序）

1. **读取 UI 设计文件**（强制）：必须读取 `zxplat-ui/apps` 中对应场景的 UI 文件，提取所有**用户可执行动作**（按钮、菜单、操作项）。
2. **抽取 IF 母表（UI 定接口列表）**：以 UI 动作为主源归纳后端能力，映射为 IF；**同一后端能力的多个触发入口（如列表查询的切队列/关键字/日期/刷新，背后都是同一个带过滤条件的查询接口）合并为一个 IF，不按 UI 输入项逐一拆分**；禁止从 DM 反向推导。
3. **读取老代码 AppService（强制）**：必须读取 `openhis-sever/openhis-application` 中同场景的既有 AppService 实现，**照搬业务逻辑**：
   - 状态流转规则（如 `PLANNED→IN_PROGRESS` 的条件）
   - 校验逻辑（如完诊前必须检查哪些字段）
   - 编排步骤顺序（先查什么、再调什么服务）
   - 异常口径（错误码、提示语）
   **禁止**：自行推断业务规则、修改校验条件、增减编排步骤。
4. **对齐 UI 与老代码**：
   - UI 有按钮、老代码有对应逻辑 → 正常生成 IF，业务逻辑照搬老代码
   - UI 有按钮、老代码无对应逻辑 → 询问用户业务规则；若需**领域写侧**新方法/事件 → 入 **DM 能力** Gap；**禁止**以「老代码/App 层无实现」 alone 入 Gap
   - UI 无按钮、老代码有逻辑 → 入 §1.4「非目标」写明舍弃（**禁止**以 UI 缺失入 Gap 表）
5. 对照 DM 校验业务逻辑：确认老代码逻辑符合 DM 状态机约束，冲突时以用户裁决为准；**注意 AS 可编排多域聚合**。
6. 写 Gap：仅 **§5.3 三类领域层缺口**可入表；逐条自检是否属「不属于 Gap」清单；若无合格缺口，§3 写「无待跟踪缺口」。
7. 自检（见 §7），不通过则继续修订。

**UI 设计文件不可访问时的处理**：
- 若 `zxplat-ui/apps` 中找不到对应场景的 UI 文件（如 `views/outpatient/doctor-station/`），**必须中断并询问用户**：「未找到门诊医生站 UI 设计文件，请确认：① 前端文件路径；② 或提供 UI 交互清单（按钮列表）」。
- **禁止**在 UI 未明确时，从 DM 状态机「补脑」用户动作生成 IF。

## 7. 自动化门禁（PASS/FAIL）

任一失败即 FAIL：
- 主章节 1~9 缺失、重排或改名；或出现 `## 10`、跳过 `## 7`/`## 8` 等与骨架不一致的章节编号。
- IF 编号与 §2 母表不一致（增删改号）；或存在已合并业务却仍占位独立 IF 编号未收敛。
- §4 未按 IF 全覆盖编排（任一 IF 无编排小节）。
- BR 未绑定 IF（存在游离规则）。
- Gap 缺失（含"无"声明也算缺失）。
- **涉及QueryService 查询时**：若DM §6.2 查询契约**已存在**且 §3 已有所需查询方法，§3 **不得**虚构「QueryService 未就绪」类 Gap；若文档**不存在**或 §3 **缺方法**，必须按 §5.3 标 **QueryService 能力** 类型 Gap。
- **Gap 语义含糊**（未标注缺口类型、或属 §5.3「不属于 Gap」却写入）→ FAIL。
- **Gap 落点非领域层**（文件+章节指向 AppService-SDD、应用层 Java、前端；或关闭条件仅要求「应用层实现/联调」）→ FAIL。
- **Gap 类型非法**（出现「应用层」「待生成代码」「缺 SDD」「缺接口」等非 §5.3 三类的类型或等价表述）→ FAIL。
- 在 AS 中出现 SDD 专属内容（包路径/字段明细/伪代码/写库顺序）。
- **业务逻辑未照搬老代码**：IF 的状态流转、校验规则、编排步骤、异常口径**必须**与 `openhis-sever` 老代码 AppService 实现一致；禁止 AI 自行脑补或修改业务逻辑 → FAIL。
- **UI 接口与老代码未对齐**：UI 有按钮但老代码无对应逻辑 → 必须询问用户并明确业务规则；仅当编排依赖**领域写侧**尚不存在能力时入 **DM 能力** Gap；**禁止**以应用层/老代码无实现 alone 入 Gap；UI 无按钮但老代码有逻辑 → 必须入 §1.4「非目标」写明舍弃；禁止直接忽略而不留痕 → FAIL。
- **UI 设计文件未访问**：未读取 `zxplat-ui/apps` 对应文件且未经用户确认 UI 清单即生成 IF → FAIL。
- **老代码业务逻辑未读取**：未读取 `openhis-sever` 对应场景既有 AppService 即自行编排业务逻辑 → FAIL。
- 正文出现来源痕迹（提及 openhis-sever/zxplat-ui/初版等）。

**业务逻辑来源与 UI 对齐（强制）**：

| 情况 | 处理方式 | 示例 |
|------|----------|------|
| UI 有按钮，老代码有对应逻辑 | **标准流程**：IF 照搬老代码业务逻辑（状态流转、校验、编排） | UI 有「开始接诊」，老代码有 `startOutpatientReception` → 照搬其状态门控和校验逻辑 |
| UI 有按钮，老代码**无**对应逻辑 | **禁止脑补**：必须询问用户该按钮的业务规则；若编排依赖**领域写侧**尚不存在的能力，入 **DM 能力** Gap 并指明 DM 需增补的方法/事件；**禁止**写「应用层待实现」类 Gap | UI 有「批量接诊」，老代码只有单条接诊 → 询问用户；若需 `batchStartReception` 则 Gap 仅指向 DM §6 缺该方法，**不**写 zxplat-app AppService 缺失 |
| UI **无**按钮，老代码有逻辑 | **明确舍弃**：入 §1.4「非目标」，写明「老代码有 {功能}，新 UI 暂未设计，本期舍弃」 | 老代码有「恢复接诊」，UI 无按钮 → 入 §1.4「非目标：恢复接诊」 |
| 老代码业务逻辑与 DM 冲突 | **用户裁决**：DM 仅用于校验，冲突时以用户说明为准，并在文档留痕 | 老代码允许状态 A→B，DM 状态机不允许 → 询问用户 |

## 8. 定稿评分（100）

- 输入完整性：20
- IF/BR/事件可追溯：25
- 编排完整与可读性：25
- 缺口表达与边界清晰度：20（§3 仅领域层三类 Gap，无应用层/SDD 类误报）
