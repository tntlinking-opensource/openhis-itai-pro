# 应用服务 SDD 文档生成提示词模板

## 1. 适用范围

- 前置：已存在对应 AS 文档（同一 AS 编码）。
- 目标：产出可直接指导代码生成的 SDD（单文件）。
- 落盘：`docs/应用/zxplat-application/AppService-SDD/`。
- **触发**：用户要求写/补 AS-SDD，或 @ 本 Skill；**禁止**热修顺手扩写。
- 命名：`AS-{域}-{子域}-{序号}-{场景名}-SDD.md`。
- 原则：章节结构与口径以本 SKILL 为唯一基线，不依赖外部模板。

## 2. 输入权威与优先级

1. 用户当期裁决（最高）。
2. 对应 AS 文档：IF、编排顺序、BR、异常、NFR（主权威）。
3. 对应 DM 文档：可调用方法、状态机、不变式、事件白名单（实现权威）。
4. **DM §6.2（*QueryService）**：查询接口契约（若涉及读侧 IF）。

限定：
- SDD 来源仅限"对应 AS + 对应 DM + DM §6.2 查询契约"。
- 既有代码、前端契约、历史 SDD仅可用于核对，不得成为新增语义来源。

冲突处理：
- AS vs SDD：AS 为业务意图权威，SDD 只做实现展开。
- DM vs **领域层**代码：命名与能力边界以 DM 为准；**领域层**文档与 `zxplat-domain` / QueryService 实现不一致时，**回写 AS §3 Gap**（类型 **代码-文档不一致**），**禁止在 SDD 内新建 Gap 表或 Gap 段落**。
- AS 与 DM 发生语义冲突：先按用户当期裁决；无裁决时以 AS 业务意图为主、DM 方法能力为实现边界；差异**仅**在 AS §3 或 §8 变更历史留痕，**SDD 正文不得出现 Gap**。
- **应用层代码尚未存在**：属 SDD 成码目标态，**不是**缺口；SDD 按 AS+DM 写全契约即可，**不得**写「待实现 AppService」「应用层缺失」。

## 3. SDD 职责边界（硬门禁）

SDD 必须写：
- 包路径、依赖注入、领域方法白名单。
- 每个 IF 的 HTTP/Request/Response 字段表（**HTTP** 须符合 **§5.3「HTTP 路径生成规则」**：**一律 `POST` 动词**，与 `AppServiceControllerRegistrar` 接入一致）。
- **领域编排序列**：按序号 **严格顺序** 可执行的 `类型#方法` 调用链（见 §5.3）；**Pre/Gate 任一失败不得进入 Cmd**。
- 写库顺序与事务边界（**§5 与 §3 编排序列中的 Cmd 对齐**，避免重复抄写整条 Pre 链）。
- 幂等/并发/容错/审计落点（关联 **§3 编排序列序号**）。
- QueryService 查询语义与事件触发的读侧刷新说明。
- **枚举、字典与值集一览（§2.3）**：本应用服务涉及的领域枚举、`*_code` 字典字段、状态/类型取值等，**逐项在对应 DM 与实现代码侧均可追溯**（见 §5.2：DM 锚点 + **代码实现锚点**）。
- 测试矩阵（可执行、可排期）。

SDD 禁止写：
- **`## 缺口跟踪（Gap）` / Gap 表 / Gap ID /「待跟踪缺口」**：Gap **仅允许出现在 AS §3**；SDD 发现领域层能力缺失时，**停止扩写该 IF 的 Cmd 链**并在交付说明中要求**先回写 AS §3**，不得在 SDD 文件内复制或新建 Gap 表。
- **App 层对外 HTTP 动词非 `POST`**：`AppServiceControllerRegistrar` **仅注册 POST**；**所有 IF（含纯查询、分页、详情）的「HTTP」列必须以 `POST ` 开头（大写 `POST`）**，**禁止** `GET` / `PUT` / `PATCH` / `DELETE` / `HEAD` / `OPTIONS` 及「REST 式读写动词区分」。读/写语义只体现在 **路径中的 `methodName` 与 Request 体**，不得用 HTTP 动词区分。
- 脱离 AS/DM 的新增 IF 或改号。
- 无来源字段"补脑"；**§2.3 中不得出现 DM 无锚点、或仅有 DM 而无代码实现锚点（含目标态计划 FQCN/`类.字段`）的枚举/字典/常量**（不得以代码仓库或 `domain-shared` 中任一 `*Constants` 接口单独作为权威来源）。
- 同一事实多处重复定义（字段、白名单、步骤）。
- **同一 Markdown 文件内出现两套完整的 `## 1`～`## 8` 章节（双稿/拼接旧版）**——交付物必须为**单一版本**，修订时删除废弃段落而非追加第二份文档。

## 4. 固定章节骨架（必须逐字同构）

1. `## 1. 实现边界`
2. `## 2. 代码结构`
3. `## 3. 按接口 ID 命名展开`
4. `## 4. QueryService 与领域事件`
5. `## 5. 写库顺序（核心写接口视角）`
6. `## 6. 非功能性需求实现（收敛为承诺表）`
7. `## 7. 测试要点`
8. `## 8. 变更历史`

## 5. 各章最小深度（强制）

### 5.1 `## 1. 实现边界`

必须包含：
- 目标与边界表（模块、边界、编排权威、方法权威、严格对齐、**实现阶段口径**）。
- 术语口径（字段口径、QueryService 口径、事务口径）。

**实现阶段口径（强制）**：
必须明确标注本 SDD 是「目标态全量契约」还是「当前已上线范围」，依赖注入表中所有类必须在对应 DM §6 或DM §6.2 中有来源。

### 5.2 `## 2. 代码结构`

必须包含：
- 包路径（到 `service/request/dto/mapper` 的类级清单；`response` 是否独立目录按工程现状，不强制）。
- 依赖注入表（含 DM §6.2 查询依赖）。
- 领域方法白名单（聚合/方法名/用于 IF）。
- **`### 2.3 枚举、字典与值集（DM 与代码可追溯）`**（固定小节标题）：汇总本 SDD 涉及的**领域枚举类**、**字典 code 字段**（含 Request/Response/DTO 中的 `*_code`、状态/类型类字段）、以及 DM 中**显式约束的取值/状态机**在实现层对应的枚举或常量。**禁止**罗列与本文 IF 无关的通用库枚举。

**§2.3 表格最小列（强制）**：

| 类别 | 代码实现锚点 | DM 追溯锚点 | 说明 |
|------|--------------|-------------|------|
| 领域枚举 / 字典字段 / 状态取值 / 公共常量（仅 DM 已约束时） / … | **必填**：见下文「代码实现锚点」规则 | **必填**：`DM-{编码}` + 章节与条目（如 **§3 实体字段表 `表名.字段名`**、**§5 状态机/事件**、**BR 编号** 等，以对应 DM 实际结构为准） | 与哪些 IF/字段相关；目标态待生成时在说明标注 |

**代码实现锚点（强制）**：每条记录必须给出读者/工具可在仓库中 **检索定位** 的实现侧标识，**禁止**仅写中文概念名或「某某状态枚举」等模糊表述。
1. **领域枚举**：写 **完整限定类名（FQCN）**（如 `com.zxplat.domain.share.enums.InventoryLedgerBusinessType`），或与 §2.1 包路径合并后可 **唯一解析** 的顶层类名并在说明中补全包（与工程/领域 SDD 一致）。
2. **Request/Response/DTO 上的字典或类型字段**：写 **`{简单类名}.{字段名}`**（如 `StartEncounterRequest.encounterStatusCode`），类名须与 §3 该 IF 字段表一致。
3. **共享常量接口**：若实现必须引用 `com.zxplat.domain.share.constants` 下某 `XxxConstants`（如 `FieldNameConstants`、`AggregateTypeConstants`），写 **`接口名.常量标识符`**；**仍须**同时具备 DM 追溯锚点，**禁止**常量单独成行而无 DM 依据。
4. **目标态（代码尚未存在）**：代码实现锚点列写 **计划采用的 FQCN 或 `类.字段`（与领域 SDD/本 SDD §2 命名一致）**，说明列标注 **「目标态待生成」**，并在 §8 变更历史留痕；**不得**留空或使用「待补充」替代 FQCN/字段名。

**DM 与代码双锚关系（强制）**：
1. **每一条** §2.3 记录必须 **同时** 具备 **DM 追溯锚点** 与 **代码实现锚点**；二者语义须一致，与 DM 或代码任一侧矛盾则 FAIL。
2. DM 追溯锚点须能唯一定位到 DM 正文中的字段、状态、事件或规则，**禁止**「见代码」「与某某模块一致」等无 DM 指向的写法。
3. 字典类 `*_code`：DM 锚点指向 DM **§3** 中该字段的定义；代码锚点指向 **实际承载该值的 API/DTO 字段**（§3 字段表已列出的类名.字段名）。
4. 领域枚举：DM 锚点对应 DM **§3** 或 **§5**；代码锚点为 **domain-shared / domain 中已有或目标态 FQCN**。
5. **禁止**以既有代码、前端常量、或任一 **`*Constants` 仓库常量**作为条目的**唯一**依据（无 DM 锚点）；**禁止**仅有 DM 而无 **可落地的代码实现锚点**（目标态须写计划 FQCN/字段名）。
6. 若实现需引用公共常量，DM 锚点须说明该取值对应的 **DM 字段或 BR**；代码锚点写 **`XxxConstants.CONST_NAME`**（与实际引用一致）或实际调用处 FQCN。

**白名单双向一致性（强制）**：白名单必须与 §3 编排序列**双向对齐**：
1. **正向**：白名单中每个方法至少在一个 IF 编排序列中被调用，禁止存在悬空白名单方法。
2. **反向**：**§3 每个 IF 编排序列中出现的所有 Cmd / Pre / Query 调用，必须在白名单中有对应条目**（类型名 + 方法名完全吻合）；禁止编排序列中出现白名单未登记的方法调用。
3. **生成完成后必须逐 IF 逐行反向检查**，将编排序列里出现的每个调用与白名单逐一比对，不符则在 §8 变更历史留痕并补入白名单。

> **包路径生成规范（直接输出，SDD 不加额外解释）**：
> - 路径结构：`{domain}/{subsystem}/{module}/`，用全称不用缩写（如 `outpatient/registration/`、`outpatient/doctorstation/encountermanage/`）
> - **就诊=encounter，管理=manage**，如 "就诊管理" = `encountermanage`
> - **Service 类**放 `service/` 子包，命名 `{Subsystem}{Module}AppService`（如 `OutpatientRegistrationAppService`、`DoctorStationEncounterManageAppService`），**不加 `Impl` 后缀**
> - **request/**、**response/** 与 §3 各 IF 入参出参类名一一对应
> - **dto/** 放列表行等复用结构体；**禁止**将 zxplat-framework / zxplat-base 等公共库已提供的共用 DTO（如 `OptionDto`）列入包路径清单，应在依赖注入表注释中注明「使用公共库 `xxx.OptionDto`」
> - **mapper/**：MapStruct **`{Name}Mapper.java`** 与工程生成/仓库常驻的 **`{Name}MapperImpl.java`**；§2.1 包路径**类级清单须同时列出**二者（与 openhis/whale 应用层现状一致，便于检索与评审）。**依赖注入、Asm 步骤与编排序列中的 `Mapper#method`** 仍以 **Mapper 接口** 为契约；不在 SDD 中展开 Impl 源码职责
> - 包路径文本块后直接跟依赖注入表，不加额外约定说明
>
> **QueryService 查询服务命名**：统一为 `{Aggregate}QueryService`，方法名与DM §6.2「接口签名」列一致（如 `page{Xxx}`, `get{Xxx}ById` 等）。

### 5.3 `## 3. 按接口 ID 命名展开`

必须先有：
- `3.1 应用服务接口（方法白名单）` 总表，列至少含：**IF**、**应用服务方法（英文）**、**中文方法名**、**HTTP**。中文名须与 AS 用户动作/接口语义一致，可与 `§3.2` 起各 IF 小节标题括号内中文互证。
- **`HTTP 路径生成规则（硬门禁，与 Whale 应用层一致）`**：**§3.1 总表与各 IF 小节中的「HTTP」列**必须按同一公式填写，且与 §2 所载 `*AppService` 一一对应：
  - **动词唯一（P0）**：**只允许 `POST`**。每一行的 HTTP 字段必须是 **字面以 `POST ` 开头**（`POST` 全大写 + 空格），**禁止** `GET` / `get` / `PUT` / `PATCH` / `DELETE` 等任何其他动词或 `post` 小写。**仅读 IF、列表查询 IF 仍为 `POST`**，不得因「查询」改用 `GET`。
  - 形态：**`POST /api/app/{serviceName}/{methodName}`**（Whale 经 `AppServiceControllerRegistrar` 将 `*AppService` **仅**以 POST 暴露为上述路径，**不**另写独立 `RestController`）。
  - **`serviceName`**：`AppService` 类名去掉后缀 `AppService` 后，将**首字母小写**（例：`OutpatientRegistrationAppService` → `outpatientRegistration`；`DoctorStationEncounterManageAppService` → `doctorStationEncounterManage`）。
  - **`methodName`**：与该 IF 对应的 **`public` 应用服务方法名逐字一致**（与总表「应用服务方法（英文）」列相同，区分大小写）。
  - **禁止**写成业务自定义 REST 资源路径（如 `/api/op/...`、`/api/outpatient/...` 等与上述公式不一致的写法）。
- **`3.1.1 编排约定（应用层如何实现 AS §4）`**（固定四类阶段 + `类型#方法` 记法），至少包含下表：

| 阶段 | 含义 | 失败时 |
|------|------|--------|
| **Gate** | 权限 / 租户 / 参数门禁 | 不再调用后续步骤 |
| **Pre** | 写前只读：加载快照、状态与 BR 门禁（*QueryService 等） | 抛业务异常，**禁止进入 Cmd** |
| **Cmd** | 领域写：*DomainService / Manager 等，持久化 + 领域事件 | 事务回滚见 §5 |
| **Asm** | Mapper 纯 DTO 装配，无领域不变式 | — |

**记法**：`EncounterQueryService#mustGetEncounter` 表示在 AppService 实现类中对 **注入的该类型 Bean** 调用该方法（运行时 Bean 名以实现为准）。

§3 章节导语必须声明：**先读完各 IF 的「领域编排序列」**，按序号从上到下执行。

然后按 IF 全量展开（不得漏 IF）：
- 小节标题格式：`### 3.x IF-xxx \`methodName\`（中文方法名）`，且与 **§3.1** 总表「中文方法名」列一致。
- Request 字段表（字段/类型/必填/说明）。
- Response 字段表（字段/类型/说明）。
- **DTO 字段表**（若 Response 中包含嵌套 DTO 类，**必须**在该 IF 下展开 DTO 所有字段，格式与 Request 表相同；**禁止**以「按 xxx QueryModel 裁剪」「字段口径见 xxx DM」等转引语句替代——字段定义必须在本 SDD 本 IF 内完整列出）。
- 关键校验。
- 失败码口径表（写接口及关键校验接口必须有）。
- **Mapper 接口方法签名**（若有 Asm 步骤，必须在此列出该 IF 对应的所有 Mapper 方法完整签名，格式：`` `methodName(入参类型1, 入参类型2, ...): 返回类型` ``；入参类型须与编排序列的「①② 结果」对应，不得留模糊描述）。
- **`领域编排序列（严格顺序）`**：表格列至少含 **`序号 | 阶段 | 调用 | 输入要点 | 说明`**；调用列必须为 **`SomeDomainService#method(CommandType)`** / **`SomeQueryService#method`** / **`Mapper#method`** 格式，**Cmd 行括号内必须写出传入的 Command 类名**（如 `PatientDomainService#registerPatient(RegisterPatientCommand)`）；**Cmd 行必须显式标注「写库点」**（多聚合时标注第一/第二写库点）。仅读 IF 在说明列标明「仅读路径」。QueryService 最终一致处用「—」行说明，**禁止**写成绕过 QueryService 直查 Repository。
  - **条件分支**：编排序列中存在 if-else 逻辑的步骤，必须在「说明」列显式写出分支条件，格式：「若〔条件〕执行本步骤；否则跳至步骤 N / 跳过」，**禁止**由读者自行推断。
  - **互斥步骤对（重要）**：当编排序列中存在两个或多个**互斥执行路径**的步骤（即只执行其中之一，例如「有已有草稿则 refresh，无草稿则 create」、「有 encounterId 则走步骤 A，仅有 slipNo 则走步骤 B」），**每个互斥步骤的「说明」列都必须写出进入该步骤的条件，并指明另一路径的跳转目标**；**禁止**将互斥路径写成无条件串行调用（串行意味着两步总是都执行，这与互斥语义不符，会产生冗余写库或逻辑错误）。
  - **参数解析**：App 层对入参的解析/转换逻辑（如多参数二选一、单号转主键等）必须作为 Gate 步骤在序列首位显式说明，不得省略或用「解析到的主键」等模糊语言代替。
- 例外：允许用「复用 IF-XXX 编排序列 1～n」引用，避免重复粘贴（引用目标 IF 必须已展开）。

**QueryService 查询调用规范**：
- 必须按DM §6.2「查询场景」表中的「接口签名」列写出完整方法名
- 格式：`{Aggregate}QueryService#{methodName}({QueryDTO}): {ReturnType}`
- 禁止写成 `{Aggregate}Repository.findAll(...)` 等底层 Repository 调用

### 5.4 `## 4~5`

- §4：QueryService 查询语义（写侧事件 -> 读侧刷新说明），不重复字段级组装细节（见 DM §6.2）。
- §5：**禁止**再次展开完整 Pre 链；必须以 **「Cmd 落库顺序一览」** 对照 §3（IF、App 方法、Cmd 序号、`DomainXxxService#method`、聚合写入顺序），并附 **事务边界 / 失败回滚** 表。多 Cmd 接口须在 §5 指明默认同一事务或可拆分策略。

### 5.5 `## 6`

必须分 `6.1~6.5`：
- 幂等性、并发控制、重试与容错、数据脱敏、审计日志。
- 关键项需写 `代码位置（必须）` 与 **`关联步骤`（引用 §3 对应 IF 下「领域编排序列」序号，如「§3.7 序号 7～10」）**。

### 5.6 `## 7`

必须分 `7.1~7.5`：
- 功能测试、非功能测试、查询结果一致性、集成测试、测试缺口跟踪。
- 表头需含：测试层级、自动化归属、优先级（P0/P1）。

## 6. 生成流程（强制顺序）

1. 从 AS §2 抽 IF 母表并锁定编号。
2. 从 AS §4 抽步骤顺序并锁定主链路。
3. 从 DM 抽可调用方法，形成白名单。
4. 从DM §6.2 抽查询服务方法，形成QueryService 查询白名单。
5. 仅依据 AS 契约与 DM/DM §6.2 查询契约语义回填 Request/Response。
5a. 从 **对应 DM §3（及 §5 状态/事件、BR）** 抽取本 AS 涉及的枚举、`*_code`、状态取值，编制 **§2.3**，逐条填写 **DM 追溯锚点** 与 **代码实现锚点**（已有代码则对齐仓库 FQCN/字段；目标态则按领域 SDD/§2 约定写计划 FQCN/`类.字段`）。
6. 写 IF 级 **领域编排序列**（Gate→Pre→Cmd→Asm）、失败码、校验口径；**§3.1 与各 IF 的 HTTP 列**按 **§5.3「HTTP 路径生成规则」** 自 §2 `*AppService` 类名与方法名推导填写。
7. 写 §5 Cmd 对照表、事务边界、NFR 承诺表、测试矩阵。
8. 对照 AS、DM、DM §6.2 查询契约做一致性复核并写变更历史（含 §2.3：**DM 锚点** 与 **代码实现锚点** 及与 §3 字段表拼写一致）。
9. **领域层能力门禁**：编排序列中每个 **Cmd** 须在 DM §6 有白名单来源；每个 **Pre/Query** 的 `*QueryService#method` 须在对应DM §6.2 有签名。若缺失 → **不得**在 SDD 写 Gap；在生成说明中列出需回写 AS §3 的条目（类型仅限：QueryService 能力 / DM 能力 / 领域代码-文档不一致），或阻塞该 IF 的 Cmd 行直至 AS 更新。

### 5.7 Gap 与 SDD 的关系（硬门禁）

| 事项 | AS | SDD |
|------|----|-----|
| 是否可有 `## 3 缺口跟踪` | **是**（唯一合法 Gap 章节） | **否**（出现即 FAIL） |
| 缺 `*DomainService` 方法 | AS §3 **DM 能力** Gap | 编排序列**不得**调用；回写 AS，**禁止** SDD 内记 Gap |
| 缺 `*QueryService` 方法 | AS §3 **QueryService 能力** Gap | 同上 |
| 缺 `*AppService` / Controller / DTO | **不是** Gap | SDD 定义目标态类名，驱动应用层生成 |
| DM 与领域代码不一致 | AS §3 **代码-文档不一致** | §8 变更历史可写「已回写 AS Gap-xxx」，**禁止** SDD 自建 Gap 表 |

## 7. 自动化门禁（PASS/FAIL）

任一失败即 FAIL：
- 主章节 1~8 缺失、重排或改名。
- IF 集合或编号与 AS 不一致。
- **§3.1 总表缺「中文方法名」列或与各 IF 小节标题中文不一致。**
- **HTTP 列违反 Whale 规则（含动词）**：§3.1 总表或任一 IF 小节的 HTTP **不是**以 **`POST `** 开头的 `POST /api/app/{serviceName}/{methodName}`，或使用了 **`GET` / `PUT` / `PATCH` / `DELETE` / `HEAD` / `OPTIONS`** 及任意非 `POST` 动词（含小写 `post`、缺空格等）；或 `serviceName` / `methodName` 与 §2 所载 `*AppService` 类名、该 IF 对应 `public` 方法名按 **§5.3「HTTP 路径生成规则」** 推导结果不一致；或出现业务自定义路径（如 `/api/op/...`）。
- **单文件存在双稿**（两套 `## 1`～`## 8` 或重复 metadata）。
- 任一 IF 缺 Request/Response/**领域编排序列**（或等价可执行的严格顺序编排）。
- 缺 **`3.1.1 编排约定`**，或调用列未使用 **`类型#方法`** 记法。
- §5 未与 §3 **Cmd 序号**对齐（写接口）。
- 写接口缺失败码口径、幂等或事务边界描述。
- 白名单存在 AS/DM/DM §6.2 查询契约无来源方法。
- **§3 编排序列中出现的方法，§2.2 白名单中无对应条目**（双向一致性反向检查：序列调用 ⊆ 白名单）。
- **编排序列中存在互斥步骤对（只执行其中之一的路径），但未在「说明」列写出每个步骤的进入条件及跳转目标**。
- 第6/7章缺承诺表/测试矩阵关键列。
- SDD 出现"AS/DM 之外"的新增业务语义来源（如直接以代码行为替代 AS/DM）。
- **任何 DTO/Response 字段表出现「按 xxx 裁剪」「字段口径见 xxx」等转引语句**（字段必须在本文完整列出）。
- **Asm 步骤对应 Mapper 方法签名缺失**（调用了 `Mapper#method` 但未在该 IF 下给出完整方法签名）。
- **Cmd 调用行未注明传入的 Command 类名**（调用格式缺括号内类型，如只写 `PatientDomainService#registerPatient` 而无 `(RegisterPatientCommand)`）。
- **编排序列中存在条件分支但未显式写出分支条件**（不得让读者自行推断 if-else 逻辑）。
- **包路径列表中包含 zxplat-framework / zxplat-base 等公共库已提供的共用 DTO 类**（如 `OptionDto` 不应出现在模块 dto/ 清单中）。
- **§2.1 `mapper/` 类级清单与工程不一致**：本仓库应用层对 MapStruct 采用 `*Mapper` + `*MapperImpl` 时，SDD **须同时列出**接口与 Impl；仅列接口而工程存在对应 `*MapperImpl` 则 FAIL。
- **缺 `### 2.3 枚举、字典与值集（DM 与代码可追溯）`**，或该小节**任意一行缺「DM 追溯锚点」或缺「代码实现锚点」**、或 DM 锚点**无法**在对应 DM 正文中定位。
- **§2.3「代码实现锚点」模糊**（无 FQCN / 无 `类名.字段名` / 与 §3 字段表类名或字段名不一致 / 仅写「某枚举」等不可检索表述），目标态未按规则标注 **「目标态待生成」** 并留 §8 留痕。
- **§2.3 出现以代码/`*Constants` 仓库常量/前端为唯一依据的条目**（无 DM 锚点或与 DM 矛盾）。
- **§2.3 仅有 DM 锚点而无代码实现锚点**（含目标态计划 FQCN/字段名）。
- **SDD 出现 Gap**（含 `## 3 缺口跟踪`、`Gap ID`、`缺口类型` 表、或「应用层待实现/缺 AppService」类缺口描述）→ FAIL。
- **§3 编排序列调用 DM §6 不存在的方法**，且 AS §3 **无**对应 **DM 能力** Gap 留痕 → FAIL（须先补 AS Gap 或删该调用）。
- **§3 编排序列调用DM §6.2 不存在的方法**，且 AS §3 **无**对应 **QueryService 能力** Gap 留痕 → FAIL。

## 8. 定稿评分（100）

- 结构完整性：20（含 **§2.3** 齐备且 **DM + 代码实现锚点** 可追溯）
- IF 契约完备性：25（含 **§3 全部 HTTP 行以 `POST ` 开头**，无 GET/PUT/PATCH/DELETE）
- 编排与方法白名单一致性：25
- NFR/事务可执行性：15
- 测试可执行性：15

总分 >= 95 方可判定为可直接代码生成输入。
