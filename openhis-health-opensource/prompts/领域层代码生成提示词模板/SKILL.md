# 领域层代码生成提示词模板

> **定位：可选插件，非主规范。** 工程门禁（JavaDoc、Repository、Flyway、禁三元、A.4 注释、B.10 常量等）**全部**在《**代码生成通用规范**》；用户日常 **只 @ 通用规范 + DM/SDD** 即可成码。  
> **何时额外 @ 本 Skill**：需要 D0–D6 占位、契约表、QueryModel 与 DM §6.2 逐行对齐等**领域对准**专用流程时。

## 使用目标

本 Skill **只解决「领域对准」**：锁定 **写哪些领域方法**、**哪些表/字段**与文档一致、**状态与契约**如何落到代码，以及本轮 **输入占位** 与 **成码后领域核对**。

**默认口径（ZXPlat）**：遵守 **[`文档代码一致性`](../文档代码一致性/SKILL.md)**——允许 **A 文档先行** 或 **B 代码先行后补文档**，但 **禁止静默漂移**（须同闭环对齐或登记 `DOC-DRIFT`）。  
成稿会话的契约输入仍为 **DM + SDD**；模式 B 时以可运行 Java 回写 DM/SDD 后再成稿/评审。发现不一致时：**模式 A 改代码；模式 B 改文档**；用户裁决优先。

**权威文档形态**

| 形态 | 说明 |
|------|------|
| **DM + SDD（均必填）** | **DM** 定义实体、状态机、BR、领域事件与领域服务方法集；**SDD** 补充方法签名、实现细节、表结构细节与测试要点。二者应保持一致；若发现冲突，记录 `DOC-CONFLICT` 后修订代码对齐 DM，并另行提出文档修订任务，不得直接绕过文档进入代码。 |

**DM 路径**：`docs/领域/DomainModel/` 下对应 `DM-*.md`；SDD 在 `docs/领域/DomainModel-SDD/`。DM 正文里对章节的文字引用（如「见 3.1」「第 6 章」）与 Markdown 标题 **`## n.`**、**`### n.m`** 指向同一处，读文档时须互相对照。

**不重复** JavaDoc 细则、`Repository`/`@Query`、Flyway 路径、`@Transactional`、JPA 注解禁令、实现类死常量、stream/for、连续闭环执行与 **A.4** 注释密度等——以上均以《**代码生成通用规范**》为准。

## 本仓库 DM 的文内体例（与 `DomainModel` 实际一致）

成码前应按文件**自上而下**扫全篇，勿只读概述。常见骨架与 `DM-WKF-009-Schedule`、`DM-WKF-007-DeviceDispense`、`DM-ADM-006-PractitionerRole` 等稿一致：

| Markdown 标题（常见） | 领域成码用途 |
|------------------------|-------------|
| **`## 1. 概述`** | 业务定义、核心职责、适用范围；跨域边界与禁止无依据编排的对照。 |
| **`## 2. 聚合根与持久化形态`** | 主/子表名、主键、高频查询；**状态机**（图示 + 状态定义表）→ D3 状态迁移表。 |
| **`## 3. 实体`** | 聚合根与子实体；**属性 / 字段名 / 类型 / 必填** 表格 → D2 字段对齐主来源（含 `### 3.2 子实体` 等多表情况）。 |
| **`## 4. 值对象（含枚举）`** | 枚举码、存储口径；与实体列一致。 |
| **`## 5. 领域事件`** | 事件类名、触发语义、载荷边界；不实现总线。 |
| **`## 6. 领域服务`** | **方法级真源**：常见为 **`### 6.1 写侧…（*DomainService）`**、**`### 6.2 读侧…（*QueryService）`**；其下 **`#### 6.x.x 中文说明（方法名）`** 标题行括号内为 camelCase 方法名（DM 内常以反引号包裹该方法名）→ 须进入 D3 契约表并落地。小节内固定条目 **业务意义 / 边界说明 / 入参 / 出参 / 前置条件 / 状态变化 / 聚合内影响 / 查询范围（读侧）/ 过滤口径 / 组装规则 / 事件输出 / 失败语义** 等 → 直接映射契约列与 JavaDoc/注释要点。 |
| **`## 7. 不变式`** | **BR-xxx**、**PR-xxx** 等规则表 → validate、状态门禁、与注释/JavaDoc 规则 ID 追溯。 |
| **`## 8. 上下文映射`** | 协作聚合与上下游；不在本聚合外写库。 |
| **`## 9. 补充`** | 意图表、FHIR 映射、与别稿对齐说明；不得覆盖第 2～7 章已写死口径。 |

**文件名习惯**：`DM-{域片段}-{编号}-{EnglishName}-{中文名}.md`（例：`DM-WKF-007-DeviceDispense-耗材发放.md`），标题行内 **限界上下文 / 聚合类型** 与包段、boundedContext 对齐时以文首元数据为准。

DM 中常见「以落库与交互契约为准」：成码需保证 **字段对齐表 + Flyway（若需）+ 实体** 三者一致；若 DM 与存量库不一致，在 **`DOC-CONFLICT`** 记录采纳依据（优先 DM 语义，其次本轮 Flyway 增量策略）。

## Whale 目标 domain 模块落盘与包划分（表前缀 / DM 域码）

领域 Java 落在 **`{目标工程}/{domain模块}/src/main/java/{业务根包}/domain/{boundedContext}/`**；**领域事件类**落在 **`{目标工程}/{domain-shared模块}/src/main/java/{业务根包}/domain/share/events/{事件分包}/`**。例如 `zxplat-aifirst/aifirst-domain/src/main/java/com/openhis/aifirst/domain/{boundedContext}/`。Flyway 默认路径仍以《代码生成通用规范》**B.3** 为准。

**boundedContext 取值规则（与表名、DM 文件名一致）**：优先采用 **DM/SDD 在本轮明确给出的限界上下文与包归属**；若文档未明确，再取物理表名 **`{前缀}_`** 的下划线前一段（或 DM 文件名 **`DM-{域码}-…`** 中的三字母域码）按下表映射为 **`{业务根包}.domain` 下的一级子包名**。下表是**默认映射与兜底规则**，不是对文档口径的反向约束；若仓库中尚无该包，**按 `administration`（`adm`）现有目录层级与命名风格新建同级包及子目录后再落代码**。

| 表前缀或 DM 域码（示例） | Java 包段（`…domain.{这里}/`） | 说明 |
|-------------------------|--------------------------------|------|
| `adm` | `administration` | 管理 / 就诊账户等 |
| `cln` | `clinical` | 临床诊疗事实（含 `cln_diagnostic_report 等） |
| `cus` | `custom` | 定制域；仓库若尚无则 **新建 `custom`** |
| `med` | `medication` | 用药 |
| `fin` | `financial` | 财务 |
| `WKF`（物理表常见） / DM 稿件 | `workflow` | 文档与 DM 常用 **WKF** 表示工作流域；落库表前缀多为 **`wkf_`**，代码包统一为 **`workflow`** |
| `dia` | `diagnostic` | 诊断相关基础域（如身体部位等）。**若目标仓库该域已统一落在 `…domain.diagnosis.*` 且与上表字面不同，为与存量一致可不迁包**，在聚合根或包说明处 `// DOC-CONFLICT` 标明与上表默认映射的差分（评审：包名 **diagnosis** vs **diagnostic** 需显式留痕，禁止静默二义）。 |
| `emg` | `emergency` | 急诊域（如分诊等） |
| `hisrm` | （已删除） | **历史 readmodel 表前缀**；2026-05-28 起读侧仅用各域 `*QueryService`，**禁止**新建 `readmodel` 包或 `hisrm_*` 表 |

**落盘补充规则（强制）**：目录按 SDD/DM 创建；ZXPlat 允许模式 B（代码先行），见 [`文档代码一致性`](../文档代码一致性/SKILL.md)。当目标包为空时，须 **从 0 创建** 与 SDD 一致的落盘路径与子目录（如 `entity/`、`repository/`、`service/`、`command/`、`queries/`、`queries/model/`、`valueobject/` 等）；不得依赖"沿用既有结构"作为唯一前置。

**事件包 `{业务根包}.domain.share.events.*`（强制分包规则）**：

1. **目录形状（必须）**：领域事件统一落在 **`{domain-shared模块}/src/main/java/{业务根包}/domain/share/events/<子域>/<主题>/`**，即 **`share/events/<boundedContext>/<topic>`** 两级结构；禁止把事件直接平铺在 `share/events/<子域>/` 根下。
2. **一级 `<子域>`（boundedContext）取值**：与领域代码 `.../domain/{boundedContext}/` 的一级包一致，优先取 **DM 文件名域码映射**（如 `DM-ADM`→`administration`、`DM-CLN`→`clinical`、`DM-CUS`→`custom`、`DM-WKF`→`workflow`、`DM-FIN`→`financial`、`DM-MED`→`medication` 等），并与本 Skill 上表保持一致。
3. **二级 `<主题>`（topic）取值**：以 **DM 的聚合英文名（EnglishName）** 为准，取其 **全小写** 作为目录名（示例：`Condition`→`condition`、`MedicationDefinition`→`medicationdefinition`、`PaymentReconciliation`→`paymentreconciliation`、`TerminologyCodeMapping`→`terminologycodemapping`、`TraceNumberRecord`→`tracenumberrecord`、`ServiceLocationTemplate`→`servicelocationtemplate`、`ActivityDefinition`→`activitydefinition`、`ServiceRequest`→`servicerequest`、`SupplyRequest`→`supplyrequest`、`SupplyDelivery`→`supplydelivery`）。
4. **禁止把技术层当二级主题**：二级 `<主题>` 只能表达业务聚合/主题（如 `condition`、`account`），禁止使用 `service`、`command`、`query`、`manager`、`projector` 等技术分层词作为 `<主题>`。
5. **新建/迁移事件时的必做动作（一次闭合）**：
   - **移动类**：把事件类迁移到新的 `share/events/<子域>/<主题>/` 目录，并同步修改 `package` 声明；
   - **修复引用**：全仓修复 `import / FQCN 引用（领域服务、QueryService、测试等）；
   - **清理旧包**：删除旧文件与空目录，避免同名类多份残留；
   - **编译门禁**：至少对受影响模块执行一次 Maven 编译验证（示例：`mvn -pl zxplat-app/zxplat-domain,zxplat-app/zxplat-domain -am -DskipTests package`；如涉及其它模块则加入对应 `-pl`）。

**每个 `boundedContext` 包内常见子目录（按类型落盘；无则新建）**：

| 子目录 | 内容 |
|--------|------|
| `entity/` | JPA 聚合根与子实体 |
| `repository/` | Spring Data **接口**，禁 `@Query` |
| `service/` | `*DomainService` 与 `*QueryService` **同一包**（两个方法集，直接实现类；与《代码生成通用规范》**B.6** 一致） |
| `command/` | 写模型 Command（**当 boundedContext 包已细化到单一聚合时，如 `…administration.patient`，Command 直接放 `command/` 根下，禁止再建同名子目录**）；当 boundedContext 包下含多聚合时，才按聚合英文全小写建子目录（例：`command/activitydefinition/`、`command/servicerequest/`）。**判断规则：若包路径末段已是聚合名 → `command/` 直接落；若末段是域名（如 `administration`、`workflow`）→ `command/{聚合英文小写}/` 分目录落。** |
| `queries/` | 查询入参对象（如 `*Query`） |
| `queries.model/` | 查询出参模型（如 `*QueryModel`） |
| `vo/` | 快照型值对象等（可选） |
| `model/`、`converter/` | 按需（`workflow` 等已有则对齐） |

**`readmodel` / `*Projector` / `*RMQueryService`（已废止）**：读侧写在各 bounded context 的 `*QueryService` + `queries/model/*QueryModel`；跨聚合读上收 **`health-module-support → `module.querysupport.*`**（见架构定稿 §5）。**禁止**新建 `domain.readmodel` 包。

**D0 填写**：`boundedContext` 先按本轮 **DM/SDD** 填写；仅在文档未明确时参考上表包段名（如 `workflow`、`administration`）。若文档已调整域划分，代码目录必须随文档调整并同步修订受影响类路径。

## 执行纪律防跑偏（强制）

为避免"只做部分对齐就提前收口"的执行偏差，本 Skill 额外增加以下**硬门禁**：

1. **范围锁定**：每轮以 DM+SDD 指定的聚合范围为准，执行中不得擅自扩缩范围；无需先输出范围声明文本，直接落盘代码即可。
2. **完成定义锁定**：`100% 一致` 最低包含以下七项，缺任一项即未完成：
   - `字段`（主/子表字段全集，含类型、可空）
   - `状态迁移`（DM §2 状态机与 §6 方法「状态变化」逐条一致）
   - `每条 BR/PR 约束范围精确实现`（逐字对照 DM §7 原文条件，不得仅凭"有落点"通过，见 D3.3）
   - `方法契约`（DM §6 全部写/读方法，含前置条件、聚合影响）
   - `事件名与最小载荷`（DM §5 全部事件）
   - `查询过滤口径（含软删）`
   - `SDD 细节条款`（分页默认排序、批量入参上限、多条时日志告警等 SDD 明确约定的行为细节）
3. **禁止阶段收口**：在上述七项未全部闭合前，禁止输出"已完成/基本完成/可进入下一域"等收口话术；仅允许在 100% 完成后输出一次性最终对账结果，若未达标则必须继续执行直至闭合。  
4. **最终输出门槛**：仅允许在"剩余差异 = 0"时宣告完成；若任一验收项未闭合，禁止输出"100%一致/已全部完成"，须明确列出未闭合项与下一步动作。附带：  
   - 文档项 vs 代码项差异清单（至少含方法、字段、事件、命令、查询）；  
   - 编译结果；lint 结果；  
   - 仍存差异时的阻断项（若非 0）。
5. **违规兜底**：若执行者中途出现阶段性收口，视为未遵循本 Skill；应立即恢复到"继续闭合差异"流程，不得以口头说明替代修复。
6. **文档与代码不符时的处理方向（强制）**：发现本仓库已落地代码（含事件包路径、方法名、字段、状态迁移等任意维度）与 DM/SDD 不一致时，**一律修订代码对齐文档**，并在差异清单与 `DOC-CONFLICT` 留痕。若文档本身疑似有误，不得在本轮代码生成中擅自修改文档——须另行提出文档修订任务，由文档生成流程（DM/SDD Skill）处理。
7. **禁止中途征询是否继续**：在未达"剩余差异 = 0"前，禁止向用户发起"是否继续/是否下一步"确认；应默认继续执行闭环。仅遇到阻断项（权限/环境/缺关键输入）时才允许暂停并请求决策。
8. **静默闭环（强制）**：
   - 在"剩余差异 > 0"期间，**禁止**输出任何阶段总结、进度播报或下一步计划；必须继续消差直至 0。
   - 仅允许在两种情况下向用户输出信息：
     1) 自判 0 差异后的最终汇报；
     2) 出现阻断项时的阻断汇报（只写阻断点与需要用户提供/裁定的最小信息）。
9. **自判完成强制检查（强制）**：在输出任何收口语句之前，必须按第 2 项验收清单逐项核对；若任一项未闭合，**禁止**输出含"如果你要"/"下一步"/"可以继续"等字样的句子，必须直接继续执行至剩余差异 = 0。

## 提示词模板

> **强制声明**：以下 fenced 块（D0 ～ D6）与本 Skill 正文条款**同等效力、同等强制**；读取本 Skill 时须逐节遵守，禁止因内容位于 fenced block 内而降级处理。**D6 验收清单**尤为关键——每一验收项与正文规范同等强制，任何一项未通过均禁止收口。

```text
你是资深DDD开发助手。请基于 **领域模型文档（DM）** 与 **软件详细设计文档（SDD）** 只生成【领域层】Java 代码（不生成 Controller、AppService、Mapper XML、前端等）。**DM 与 SDD 均为必填输入**，缺任一份请先补充文档再进入代码生成。

- **DM + SDD**：DM 的 **`## 2.`～`## 7.`** 为结构与行为主真源；SDD 补充方法签名、实现细节与测试要点。二者冲突时修订代码对齐 DM，记录 `DOC-CONFLICT`；文档疑似有误则另立文档修订任务。

**权威范围**：以 DM 的 **`## 2.`～`## 7.`** 为结构与行为主真源；**方法名与写读契约**以 **`## 6. 领域服务`** 为主，**SDD 可细化签名与测试列**；方法契约通过代码 JavaDoc 体现。禁止虚构未在 **DM 或 SDD** 中出现的核心写语义。

**强制前置**：你必须完整遵守项目 Skill《代码生成通用规范》的全部条款，包括但不限于：**0. 门禁总览**（含 **§0.16** 编排类 `private` 默认内联）；**A.4**（编排类逐分支/逐步业务 `//`、`忌废话` 边界、注释验收一致）；**A.10**（连续闭环执行至 0 差异后再汇报，未达标不得收口）；**B 节**（JavaDoc、Repository、Flyway、编排禁码表、类内顺序、**B.5.1 / B.5.1.1（禁止薄包装 `private`：`domainNow`、`defaultNow`、单行 `now`/`resolve`/`load` 等）**、分包、Manager 冻结、`@Transactional`、实体注解禁令、constant 包等）。

# D3. 领域方法、状态与契约（领域专属）

1. **状态迁移**必须封装在聚合方法中；禁止外部直接 `setStatus`。
2. **服务层禁止直接状态枚举比较（硬门禁，新增）**：
   - `*DomainService` 方法体内**禁止**出现 `XxxStatus.XXX.getCode().equals(entity.getStatusXxx())` 形式的直接枚举比较。
   - 所有状态门禁校验必须委托聚合根 `assertXxx()` 方法完成，服务层只能调用该方法，不得内联实现状态判断逻辑。
   - **自检模式**：生成完成后搜索 `DomainService` 文件，若发现 `Status.getCode().equals(` 模式，必须将其提取为聚合根 `assertXxx()` 方法并替换调用。
3. 每个写方法：**前置校验（validate）→ 再改状态或字段**。
2.1 **默认双形态 Command（强制，领域层专属规则）**：
- **默认双形态**：所有 `*DomainService` 写方法的顶层 Command 默认同时持有 `item`（单条）与 `items`（批量列表），`items` 优先，`item` 与 `items` 均为 null/空时直接拒绝。无需 SDD 在字段全集表中逐方法声明，AI 自动生成包装结构。
- **Command 结构分层**：顶层 `XxxCommand` 持有 `item: XxxItemCommand`、`items: List<XxxItemCommand>` 及 `operatorId: Long` 等顶层审计字段；内层 `XxxItemCommand` 只持有 SDD 字段全集表中列出的业务字段，不含 `item`/`items` 包装字段，不含 `operatorId` 等顶层审计字段。
- **SDD 字段表约定**：SDD 命令字段全集表只列业务字段与 `operatorId` 等顶层审计字段，**禁止**列 `item`/`items` 行——包装结构由本规则隐式添加。
- **单条覆盖（唯一例外）**：当且仅当 DM 或 SDD 该方法描述中**明确出现**"不支持批量"/"单次操作"/"一次仅处理一条"等字样，才生成仅 `item` 的单条 Command；否则一律双形态。
- 批量 I/O 实现约束（禁循环落库、内存去重、唯一性下推）见《代码生成通用规范》A.9.1。
2.2 **前置条件逐条落地规范（硬门禁）**：DM `§6.1.x` 各方法小节"**前置条件**"列出的所有约束**必须全部落地**，不得遗漏：
   - **聚合内可直接检查的前置条件**（如状态校验、字段格式、必填验证）：必须在领域方法或聚合根方法中实现，不得缺失。
   - **跨聚合引用检查的前置条件**（DM 原文通常写为"当前无进行中的 Encounter""无活跃引用"等）：领域层无法直接访问其他聚合，须在领域服务方法头 JavaDoc 中用 `@preconditions` 明确标注"此约束需由应用服务层在调用本方法前完成跨聚合校验"，并同步在 DomainService 对应方法 JavaDoc 中注明；**禁止**在代码中无声地忽略 DM 中已明确列出的跨聚合前置条件。
   - 约束文字描述范围缩小或扩大均须标记 `DOC-CONFLICT`，与第 3 条 BR 精确规范保持一致。
2.3 **Command 子命令类型独立性（硬门禁）**：每个 Command 类中的内层 `XxxItemCommand` **必须**作为该 Command 的独立静态内部类声明；**禁止**跨 Command 复用内部静态类（如在 `SyncXxxCommand` 中引用 `RegisterXxxCommand.IdentifierItemCommand`）。跨 Command 类型依赖会导致一个 Command 的字段变更无意中影响其他 Command 的语义，破坏命令边界的独立性。若多个 Command 确需共享证件项类型，须将共享类型单独提取为顶层或 `command` 包级别的共享类（如 `IdentifierItemCommand`），而非寄宿在某一 Command 内部。
2.4 **Command 字段使用完整性（硬门禁）**：Command 及其内层 `XxxItemCommand` 中声明的每个字段，在对应的 `DomainService` 方法中**必须有至少一处实际读取**（赋值到实体、传入校验、传入事件构造函数等）；生成完成后须逐字段核对，存在"声明但从未在服务层读取"的死字段须**移除或补充使用逻辑**，禁止保留永不生效的占位字段。
2.5 **SDD entityInvariantMethod 必须落地到聚合根实体（硬门禁）**：SDD 各写方法小节中 `entityInvariantMethod` 列出的方法名（如 `assertXxx`、`initXxxByYyy`、`markXxx`、`assertStudentRecordUpsertable` 等）**必须**作为聚合根实体的 `public` 方法落地；**禁止**将 SDD 规定的实体不变式方法降级为 `DomainService` 中的 `if-else` 内联逻辑。领域规则属于聚合根——服务层只调用聚合根方法，不自持领域判断逻辑。若某不变式无法在聚合根实现（如需访问仓储），须在方法 JavaDoc 中说明原因并在 `DOC-CONFLICT` 留痕，但不能静默省略。
3. 每条核心业务规则 **BR-xxx**（及 DM 中的 **PR-*** 等）须同时满足以下三点，缺一不可：
   - **有落点**：至少一处校验或不变量体现，注释或 JavaDoc 可追溯到规则 ID；
   - **约束范围精确（强制）**：必须逐字比对 DM §7 原文的约束条件文本，确认代码中的校验范围、触发条件与 DM 完全一致——不得仅凭"有一个同名方法"视为通过。典型错误示例：唯一性约束原文写"含已逻辑删除记录"，代码只查 `isDeletedFalse` → 视为 **BR 未闭合**；状态门禁原文写"active 或 draft 均可触发"，代码只校验 `active` → 视为 **BR 未闭合**。约束范围缩小或扩大均须标记 `DOC-CONFLICT` 并修复代码。
   - **仓储判定与 BR 语义一致（强制，防 P1-N1 类错误）**：用于支撑某条 BR 的 `repository.*` 调用，其**查询语义必须能推出** DM §7 中该 BR 的命题为真。**禁止**「有调用即算落地」而方法实际表达的是别的含义。反例：BR 要求「删除前无医嘱引用」，却用 `countByIdAndIsDeleted(...)` 仅判断「该 id 是否存在非删行」（结果恒为 1），与「医嘱引用」无关 → **BR 未闭合**。**自检**：每条涉及 BR 的 `DomainService` 方法，用**一句人话**写清「BR 原文 → 哪次仓储调用的结果如何支撑该句」；对不上则不得收口。
4. **状态机约束**：实现中禁止出现 DM §2 状态机与 §6 各方法「状态变化」之外的状态迁移；状态迁移必须封装在聚合方法中，直接在代码中体现，无需先输出状态迁移 Markdown 表格。
5. **领域方法覆盖**：DM+SDD 中每个写侧方法小节（括号内方法名）必须在代码中落地；**不得**实现文档之外的核心写语义方法；读侧同理。无需先输出 Markdown 契约表，方法契约直接在代码 JavaDoc 中体现（`@preconditions`、`@state-transition`、`@throws` 等）。
6. **领域事件**：只定义类与最小 payload；不实现发布总线；事件名以 **`## 5. 领域事件`** 为准，**SDD 可补命名与载荷**；若文档写「以实现为准」或事件未单列，可记录占位策略，**禁止**无依据臆造事件名。
6.0 **「设计预留」/不发布（硬门禁）**：DM `§5` 对某事件若注明 **「设计预留」**、**「当前未见/不发布」** 或**未规定**在 `§6` 写方法中发布，则 `*DomainService` 中**禁止** `domainEventPublisher.publish(该事件)`。与 **D3.8.6** 区分：后者管子表仓储是否注入；本条管**无文档依据的提前发事件**。若产品确需发布，须先修订 DM/SDD 去掉「不发布」类表述后再成码。
6.1 **事件载荷逐字段对齐（硬门禁）**：DM `§5.1` 事件表"**携带数据**"列列出的每个字段**必须全部出现在事件类中**，不得遗漏（如 `operatorId`、`busNo` 等）；生成事件类后须逐字段比对 DM 事件表，缺一字段即视为未完成。
6.1.1 **SDD 事件载荷扩展行与 DM 并集（硬门禁）**：若 SDD 存在**独立的事件与载荷表**（常见为某章 **「领域事件」/「事件与载荷」**，编号因稿而异，如 §5～§7），且列出的字段**多于** DM `§5.1` 同一事件，则事件类字段须为 **DM 与 SDD 的并集**（同类冲突以 **DM 优先** 并 `DOC-CONFLICT`）。**禁止**用仅含 `busNo`、`operatorId` 的极简骨架代表该事件通过验收（评审：多聚合出现「压缩载荷」类 P1）。
6.2 **事件载荷字段语义精确性（硬门禁，新增）**：
   - **区分"业务标识"与"技术主键"**：
     - **业务标识**：人可读、用于业务识别的字段（如"学号"`studentNo`、`busNo`、`idCard`），通常是 `String`；
     - **技术主键**：数据库自增/雪花 ID（如`studentId`、`patientId`），通常是 `Long`。
   - DM §5.1 写"学号"的，禁止用 `studentId`（技术主键）替代；写"患者标识"的，禁止用 `busNo`（业务编码）替代。
   - **自检步骤**：生成事件类后，逐字段对照 DM §5.1 "携带数据"列的**业务语义描述**（而非字段名相似度），确认字段类型与语义匹配；不匹配时标记 DOC-CONFLICT 并修正。
6.2 **事件变更摘要禁止硬编码（硬门禁）**：当 DM 载荷描述为"变更字段摘要"或"变更内容"等动态信息时，**禁止**在服务层用静态字面量列表（如 `Arrays.asList("profile")`）替代；应在服务层根据实际入参计算变更字段集合后传入事件构造函数，或在事件类型设计上允许接收动态字段列表。
7. **禁止**在本领域服务中编写跨域编排（如支付联动库存、发票、医保等无 **DM/SDD 依据** 的联动）。DM 已写明「由应用服务/协作域处理」的，领域层仅收口本聚合状态与事实字段。
8. **横切行为约束（硬门禁，逐点执行）**：以下约束对**全部**写方法普遍适用，生成后须逐方法检查，不得仅对"主干流程"落地而在边界场景静默跳过：
   - **8.1 终止态不可逆保护**：凡涉及状态迁移的聚合方法（`transitToXxx`、`initXxx`、`markXxx` 等）**必须**在执行迁移前调用或内置终止态检测逻辑（如 `assertNotTerminal`），防止已处于 `DISCHARGED`/`CANCELLED`/`ENTERED_IN_ERROR` 等终止态的聚合被重复迁移；`EncounterStatus.isTerminal()` 类工具方法存在时**必须**复用。禁止仅在 BR 列表里文字提及而不在每个迁移方法中落点。
   - **8.2 完诊/出院双重校验**：凡方法契约包含"完诊"或"出院"语义（含 `complete`、`discharge` 等），须同时校验 **(a) 负责医生参与者存在** 和 **(b) 主诊断存在**；两项缺一视为 BR 未闭合，须各自有独立的校验调用点。
   - **8.3 接诊/换医生时旧参与者必须收口**：凡方法包含"接诊"或"切换责任医生"语义，必须先查出同角色的活动参与者并调用 `markCompleted`，再写入新参与者；禁止仅新增参与者而跳过旧参与者收口，否则同一角色会出现多条并发活动记录。
   - **8.4 收尾类方法须加载聚合根并校验状态**：凡方法只操作子表（如清床仅操作 `EncounterLocation`）但业务语义有前提状态（如"仅 DISCHARGED 后可清床"），必须先加载聚合根实体并通过 `assertXxx` 校验状态，禁止跳过聚合根直接写子表。
   - **8.5 upsert 主诊断唯一性须跨库检查**：执行诊断 upsert 时，主诊断唯一性约束**不能仅在入参集合内校验**；需查询该就诊在数据库已有的活动诊断记录，综合判断新旧合计是否超过一条主诊断，否则已有主诊断不会被感知。
   - **8.6 子表仓储使用检查（区分有写方法关联 vs 仅预留）**：判断标准以 **DM/SDD §5 写方法白名单** 为准：(a) 若某张子表在白名单中有对应写方法（如 `upsertXxx`、`addXxx`），则对应仓储**必须**被注入并在该方法中调用，否则子表数据永远为空；(b) 若某张子表仅在 §3 字段定义与 §4.5 仓储接口中声明，但 §5 写方法白名单中**无任何方法涉及该子表的写入**，则仓储可以暂不注入——这属于"预留仓储待后续迭代实现"，**不视为缺陷**。禁止将"预留仓储未注入"和"有写方法但仓储未调用"混淆处理。
   - **8.7 防重校验需数据库唯一索引兜底**：仅靠 `exists` 查询的应用层防重在并发写场景存在 TOCTOU 窗口；生成防重逻辑时须在 JavaDoc 中注明"依赖数据库层 `busNo`/唯一键索引保障最终一致性"，不得将应用层 `exists` 视为完整保障。
   - **8.8 禁止跨聚合读（P0，与《代码生成通用规范》B.6.4 同档）**：`*QueryService` **只注入本聚合 `*Repository`**；**禁止**他聚合 `*QueryService`/`*Repository` 注入与 EM 跨根 `exists`/`join`。**跨聚合只读唯一落点** `module.querysupport.{域}.*Loader`（示例：`PractitionerRoleScopeLoader` → `resolvedPractitionerIdsForRole` 入参）。成码后 grep touched 聚合目录：`subquery`/`cb.exists`/跨包 `entity` import。

# D5. 执行与汇报（引用全量规范）

默认执行**持续闭环**：对本轮文档范围内全部内容（字段、状态、枚举、`DomainService`、`QueryService`、`Command`、子表实体与仓储/事件等）持续执行"差异识别 → 改码 → 编译/校验 → 继续消差"，直至剩余差异为 0。

禁止阶段性进度汇报；未达 0 差异前不得请求用户确认是否继续（静默规则见 **执行纪律 8**）。

**多聚合批量生成时的逐聚合 D6 验收（硬门禁）**：当本轮任务涉及 **≥ 2 个聚合**的代码生成时：
- 每完成**一个聚合**的全部文件（entity、repository、command、service、event）生成后，**必须立即执行一次 D6 验收清单**，逐项核对字段完整度、枚举值、批量 I/O、子实体等，通过后才能开始下一个聚合；
- **禁止**等所有聚合全部跑完再统一做一次 D6 验收——长会话上下文衰减会导致越靠后的聚合问题越集中，且最终统一验收时早期问题已难以追溯；
- **编译通过 ≠ D6 通过**：`mvn compile` 成功只验证语法，不验证字段完整度与文档对齐；D6 验收必须额外完成，不得以编译成功代替。
```
