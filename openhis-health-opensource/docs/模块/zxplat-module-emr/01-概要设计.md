## 一、概述

### 1.1 文档目的

- 在功能清单基础上，明确系统架构、模块划分、核心数据模型与接口边界。
- 为详细设计（前端组件、服务端 API、数据库表结构）提供统一约束与依赖顺序。

### 1.2 依据与范围

- **功能依据**：`功能清单.md` 第五节的「功能清单」及「实现要点」、第三节的「按实现顺序的优先级」。
- **范围**：电子病历文书编辑、存储、模板、打印（PDF）、留痕、权限与审计、诊断/检查检验对接、质控与归档等；OFD、静默打印为裁剪项，见功能清单第一节。

### 1.3 技术栈与边界

| 层次 | 技术 | 职责边界 |
|------|------|----------|
| **前端** | Tiptap（ProseMirror）+ Vue | 富文本与结构化编辑、自定义块/节点（区域、数据组、数据元）、模板与书写模式、JSON 交换；不负责真实分页与打印机续打。 |
| **服务端** | Java（**zxplat-framework**） | 文档/模板 CRUD、权限与审计、诊断/检查检验对接、保存前校验、接收 JSON 并驱动 OpenPDF 生成 PDF；分层架构、AppService 自动 API、多租户与审计见下节。 |
| **PDF** | OpenPDF | 服务端将文档内容渲染为 PDF（分页、页眉页脚、水印、页码）；按页/按范围输出；不依赖浏览器打印。 |

**前端技术栈与集成**：Vue 3.x、构建工具（Vite/Webpack 等）、建议 TypeScript；状态管理（Pinia/Vuex 等）。与 whale 前端（若有）的集成方式：独立 SPA 或嵌入、路由与菜单、统一认证（Token）由网关或请求头传递。具体版本与选型在详细设计中确定。

### 1.4 运行环境与部署

- **服务端**：Java 17、Spring Boot 3.x（与 zxplat-framework 一致）、PostgreSQL 16+。与 zxplat-framework 同进程部署（zxplat-module-emr 作为业务模块）或独立进程由项目决定。
- **前端**：Node 18+；构建产物静态部署或与网关集成。
- **容器化**：若使用 Docker/K8s，镜像与配置见部署文档。

## 二、名词定义（术语表）

以下术语在本概要设计及后续详细设计、接口与数据模型中统一使用，便于理解与沟通。

| 术语 | 英文/技术对应 | 定义 |
|------|----------------|------|
| **数据项名** | data item name / `attrs.name` | 区域、数据组或数据元在文书/模板中的**唯一标识名**，对应 Tiptap 节点上的 `attrs.name`（或 `attrs.id`）。用于按名取值/赋值、结构解析、按区域打印、质控必填段、统计与检索等。同一文档内同一层级建议不重名。示例：主诉、现病史、血常规、体温。 |
| **区域** | Region | 文书内的逻辑分区，对应病历的段落/章节（如主诉、现病史、体格检查）。自定义 Block 节点，含数据项名、标题、必填/参与打印/保护等属性。 |
| **数据组** | Section | 可重复或可嵌套的结构块（如既往史多条、阳性体征列表）。自定义 Block 节点，含数据项名、标题、可删可改等属性。 |
| **数据元** | DataElement | 最小录入单元，对应病历字段：文本框、数值、日期、下拉、多选、复选框等。自定义 Node + NodeView，含数据项名、类型、value 等；按数据项名取值/赋值。 |
| **模板** | Template | 某类文书的标准结构：预置好的区域、数据组、数据元（含数据项名与类型），内容可为空或默认值。存储于 emr_template 表，新建文书时可复制其 content 作为初值。 |
| **文书类型** | Document Type | 文书分类配置（如入院记录、病程记录、出院小结），对应 emr_document_type 表；可绑定默认模板。 |
| **书写模式** | Write Mode | 仅允许在数据元内填写，禁止增删改区域/数据组结构的编辑模式；与「模板编辑模式」相对。 |
| **content** | document content | 文档或模板的正文数据，以 Tiptap/ProseMirror 的 **JSON** 形式存储于 emr_document.content / emr_template.content；内含区域、数据组、数据元等节点的树形结构。 |
| **按数据项名取值/赋值** | get/set by name | 通过数据项名（或 id）在文档 JSON 中定位节点并读取或写入 value；用于诊断带入、检查检验引用、批量填充、统计等。 |

**说明**：实现时区域/数据组/数据元的 `attrs.name` 即本系统所称的**数据项名**；若需加速按数据项名检索或统计，可将数据项名单独持久化（见 6.6、6.7）。

## 三、系统架构

### 3.1 总体架构

```
┌─────────────────────────────────────────────────────────────────┐
│  浏览器 / 前端 (Vue + Tiptap)                                    │
│  - 患者/文书列表、文档打开/保存、富文本与结构化编辑                │
│  - 区域/数据组/数据元（自定义 Node + NodeView）                   │
│  - 模板选择、书写模式、留痕视图、打印预览（PDF URL）               │
└───────────────────────────┬─────────────────────────────────────┘
                            │ HTTP/HTTPS（JSON、PDF 流）
┌───────────────────────────▼─────────────────────────────────────┐
│  Java 服务端                                                    │
│  - 文档服务、模板服务、用户与权限、审计                           │
│  - 诊断/检查检验对接、LIS/PACS、就诊上下文（patientId/encounterId） │
│  - 文档校验、结构解析（不打开文档）、版本与留痕存储               │
│  - 调用 OpenPDF 生成 PDF（预览/下载/续打/多文档合并）             │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│  存储与外部系统                                                 │
│  - 文档/模板/版本存储（DB 或对象存储）                            │
│  - HIS、LIS、PACS、字典/诊断/检查检验接口                        │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 数据流要点

- **打开文档**：服务端按文档 ID 或患者+文书类型返回文档 JSON → 前端 Tiptap `setContent`。
- **保存文档**：前端 `getJSON()` 提交服务端 → 服务端校验、落库、可选版本快照。
- **打印/导出 PDF**：前端提交当前文档 JSON（及可选参数：页范围、**数据项名**列表、页眉页脚、水印）→ 服务端 OpenPDF 渲染 → 返回 PDF 流或 URL。

### 3.3 服务端与 zxplat-framework

Java 后端**基于 zxplat-framework 开发**，与 zxplat-domain 等业务一致，复用框架的分层、认证、权限、审计、多租户与自动 API 能力。EMR 为插件工程 `zxplat-plugin/zxplat-module-emr`，依赖 `zxplat-framework`；文书领域与 AppService 落在 EMR 各层，PDF 渲染（OpenPDF）在 `module-emr-application`。HIS 读写经 `module-emr-bridge` 调用 `zxplat-domain`。详见第四节与 [17-zxplat-module-emr-架构-v3.md](./17-zxplat-module-emr-架构-v3.md)。

**与 zxplat-domain 等业务模块的关系**：若与 zxplat-domain 等同仓部署，可共用 zxplat-framework、统一认证与菜单；EMR 菜单与权限由权限模块配置。若独立部署，认证通过 JWT 或网关与现有系统对接。

## 四、服务端技术栈与 zxplat-framework 约定

### 4.1 框架定位与 EMR 依赖

- **zxplat-framework**：基于 ABP 标准的 Java 企业级应用框架（Spring Boot 3.x、Java 17、PostgreSQL、Layered Monolith）。提供：分层架构（Domain / Application / Infrastructure / Web）、多租户（共享库+共享表，Header `X-Tenant-Id`）、审计日志、工作单元（@Transactional）、JWT 认证、权限（基于角色）、自动 API（AppService 自动暴露 REST）、Flyway 迁移、MapStruct 映射、统一异常与响应格式。
- **EMR 后端依赖的框架模块**（建议）：
  - **zxplat-framework**：BaseAuditedEntity、IMultiTenant、统一异常（BusinessException/EntityNotFoundException/ValidationException）、Result、ID 生成等。
  - **zxplat-framework**：用户、登录/会话、JWT。
  - **zxplat-framework permission**：按角色/权限控制接口与菜单。
  - **zxplat-framework audit**：操作审计（打开/保存/打印等可对接审计）。
  - **zxplat-framework**：自动 API 控制器（AppService 暴露为 `POST /api/app/{serviceName}/{methodName}`）、全局异常处理。
  - **zxplat-framework tenant**（可选）：若 EMR 需多租户隔离，实体实现 IMultiTenant，Header 传租户 ID。

### 4.2 zxplat-module-emr 后端模块与分层

| 模块 | 职责 | 依赖 |
|------|------|------|
| **module-emr-domain** | 文档、模板、文书类型、版本/留痕等实体；Repository；领域服务；loader / PDF 端口 | zxplat-framework |
| **module-emr-bridge** | ContextLoader 实现、ExtensionImpl、诊断同步 Orchestrator | module-emr-domain、zxplat-domain、zxplat-framework |
| **module-emr-application** | 文档/模板/PDF/元数据等 AppService；Request/Response；Flyway(emr)；PDF 适配器 | module-emr-domain、zxplat-framework |
| **module-emr-starter** | 安装入口（聚合三层，无业务源码） | domain + bridge + application |

- **包名**：`com.zxplat.plugin.emr.*`；ExtensionImpl 在 `com.zxplat.plugin.emr.bridge.integration`。
- **分层**：Domain / Bridge / Application 四模块（含 starter）；**无**独立 infrastructure 子模块。细规见 [17-zxplat-module-emr-架构-v3.md](./17-zxplat-module-emr-架构-v3.md)。

### 4.3 开发约定（与框架一致）

| 约定项 | 说明 |
|--------|------|
| **AppService 与自动 API** | 服务端业务接口类名以 `*AppService` 结尾（如 `DocumentAppService`）；zxplat-framework 自动暴露为 `POST /api/app/{serviceName}/{methodName}`，**serviceName** = 类名去掉 `AppService` 后缀并首字母小写（如 `DocumentAppService` → `document`，`TemplateAppService` → `template`），**methodName** = 方法名。请求体为 JSON 数组 `[arg1, arg2, ...]`。所有业务接口均通过 AppService 暴露，不手写 Controller。 |
| **实体** | 实体类**不使用 Entity 后缀**（如 `Document`、`Template`，不用 DocumentEntity）；继承 `BaseAuditedEntity`；若多租户则实现 `IMultiTenant` 并设 `tenantId`。ID 使用 Long（雪花算法）。 |
| **DTO/Request** | 输出用 `XxxDto`；创建用 `CreateXxxRequest`、更新用 `UpdateXxxRequest`（**更新必须含 id**）；查询用 `Query{Entity}Request`（如 `QueryDocumentRequest`），继承 `BaseQueryRequest` 时分页由基类提供。**多参接口合并为单一 Request 对象**，禁止多参方法签名；单 id 操作（如 getById、delete）使用 `IdRequest` 或 `DeleteXxxRequest`，禁止 `getById(Long id)` 等基本类型入参（见框架《API参数标准化说明》）。 |
| **领域层 Command/Query** | 写操作参数封装为领域层 `command` 包下的 `CreateXxxCommand`/`UpdateXxxCommand` 等；查询条件封装为 `query` 包下的 `XxxQuery`（仅查询条件，不含分页）。Application 层 Request 转 Command/Query 通过 Mapper 或在 AppService 内转换。 |
| **对象映射** | **必须使用 MapStruct** 做 Entity↔DTO、Request→Command 等映射；**禁止使用 BeanUtils**。Mapper 接口 `componentModel = "spring"`，`nullValuePropertyMappingStrategy = IGNORE`。 |
| **异常** | 使用框架统一异常：`BusinessException`、`EntityNotFoundException`、`ValidationException`、`UnauthorizedException`；校验失败返回 ValidationException 或结构化错误列表。 |
| **Flyway** | EMR 迁移随 **`module-emr-application`** 资源发布（`META-INF/zxplat/flyway-module.json`），由 zxplat-domain Flyway 编排加载；开关 `zxplat.modules.emr.enabled`。 |
| **权限与审计** | 需控制的操作（如保存、打印、模板管理）可加权限注解；打开/保存/打印等可写入审计（对接 zxplat-framework audit 或自定义审计表）。 |

**错误码与前端展示**：校验失败、权限不足、实体不存在等使用框架 ValidationException/UnauthorizedException/EntityNotFoundException；前端根据 Result 的 success、errorCode、message、errors 展示 toast 或表单错误。若有统一错误码表，见详细设计或 API 文档。

以上约定**必须**与 ZXPlat Framework 文档一致：编码规范见 [`framework/02-开发规范.md`](../../框架/02-开发规范.md)，架构见 [`framework/00-框架概览.md`](../../框架/00-框架概览.md)；Flyway 模块化规则以 [`01-架构/模块化开发规范.md`](../../架构/模块化开发规范.md) 为准。

### 5.3 PDF 渲染与预览（OpenPDF 集成）

> 可渲染节点清单、PrintConfig 可配置项、预览触发策略见《[打印预览设计](04-打印预览设计.md)》。

| 能力 | 说明 |
|------|------|
| **文档 → PDF** | 将 ProseMirror/Tiptap JSON 转为流式排版；支持自定义节点（区域、数据组、数据元、分页符、表格、图片等）的渲染规则；按 MVP→v3 分阶段实现。 |
| **双层预览** | **L1**：emrEditor A4 纸面即时反馈；**L2**：同一 `OpenPdfRenderer` 生成 PDF 预览（防抖/手动刷新，禁止每键请求）。 |
| **PrintConfig** | 纸张、页边距、页眉页脚、水印、字体等与 content 分离；来源：系统默认 → 文书类型 → 模板 → 请求体。 |
| **分页与版式** | 分页符节点触发分页；页边距、页眉页脚高度由 PrintConfig（mm）传入。 |
| **页眉页脚** | PdfPageEventHelper 在每页绘制；首页可不同；支持「第 X 页 / 共 Y 页」及占位符（患者、文书类型等）。 |
| **水印** | PdfContentByte 在每页绘制文字水印；previewMode 可简化；正式打印按策略强制。 |
| **续打与范围** | 支持 pageRange、regionNames（按数据项名）；块→页号由渲染过程记录或预解析得出。 |
| **多文档合并** | 多份文档分别渲染为 PDF 后合并为一 PDF；页眉页脚可统一或按文档区分。 |
| **留痕** | includeTrackChanges 控制；渲染带删除线/高亮等 mark 的 JSON。 |
| **previewMode** | true：预览（可限页、不写打印审计）；false：正式打印/归档。 |

| 启用 | 布尔 | |

### 6.4 版本与留痕

| 概念 | 说明 |
|------|------|
| **版本** | 每次保存可存一份快照或 diff；版本列表含版本号、时间、操作人；回滚即用某版本内容写回当前文档。 |
| **留痕** | 前端用 Tiptap mark（如 insertion/deletion）或服务端 diff 生成带 mark 的 JSON；痕迹列表、提交（落稿）由服务端存元数据并可在提交后生成新版本。 |
| **逻辑删除** | 节点级 attrs.deleted；渲染时按配置隐藏或灰显。 |

### 6.5 文档 JSON 结构约定

- **根**：ProseMirror doc，含 `content` 数组（block 节点序列）。
- **区域**：自定义 Block Node，`attrs`: id、**数据项名** name、title、必填/参与打印/保护等。
- **数据组**：自定义 Block Node，可嵌套，`attrs`: sectionId、**数据项名** name、title、可删可改等。
- **数据元**：自定义 Node + NodeView，`attrs`: id、**数据项名** name、type、value 等；按**数据项名**做取值赋值。
- **分页符**：自定义 Block Node（如 `pageBreak`），OpenPDF 渲染时遇之分页。
- **留痕**：通过 mark 或节点属性表示插入/删除，OpenPDF 渲染时保留删除线/高亮。

后续可在详细设计中提供 ProseMirror/Tiptap 的 JSON Schema 或类型定义，并约定 doc 根节点 version 或 meta.version 用于兼容扩展。

### 6.6 存储与表结构建议

| 项 | 建议 |
|------|------|
| **表名** | `emr_document`、`emr_template`、`emr_document_type`（文书类型）、`emr_document_version` 等；与 Flyway 脚本命名一致。 |
| **content 存储** | PostgreSQL 使用 JSONB 或 CLOB；若单文档过大可考虑压缩（如 gzip）或分块表，大小上限见功能清单「非功能需求」。 |
| **索引** | 文档表：患者/就诊/文书类型/状态、创建时间；模板表：编码、启用状态；版本表：文档 id、创建时间。 |
| **数据项名索引（可选）** | 若需按**数据项名**快速检索或统计（如按「血常规」查文书），可增加表如 `emr_document_data_item_index`（document_id、node_type、数据项名、可选 result_id 等），在保存文档时解析 content 写入；见 6.7.2。 |
| **多租户** | 若采用 IMultiTenant，表增加 `tenant_id` 及索引。 |

### 6.7 阶段 2（结构化）与阶段 3（模板与模式）的业务含义与持久化

以下针对「阶段 2：结构化」与「阶段 3：模板与模式」补充业务含义及与持久化的对应关系，便于详细设计与实现对齐。

#### 6.7.1 阶段 2：结构化的业务含义

| 概念 | 业务含义 | 在 EMR 中的用途 |
|------|----------|-----------------|
| **区域（Region）** | 文书内的逻辑分区，对应病历中的**段落/章节**（如「主诉」「现病史」「体格检查」「专科检查」）。 | 分段展示与折叠、按区域打印/续打、质控必填段、不打开文档解析时按区域提取或过滤。 |
| **数据组（Section）** | 可重复或可嵌套的**结构块**（如「既往史」下的多条记录、「阳性体征」列表）。 | 结构化录入与展示、按数据组取子树文本、按属性过滤（如参与打印、可删可改）。 |
| **数据元（DataElement）** | 最小录入单元，对应病历中的**字段**：单行/多行文本、数值、日期、下拉、多选、复选框等。 | 按**数据项名**取值/赋值（诊断带入、检查检验引用、批量填充）；必填与校验；字典/诊断/检查项目联动。 |

**按数据项名取值/赋值**：通过**数据项名**（节点 `attrs.name` 或 `attrs.id`）在文档 JSON 中唯一定位；诊断带入、检查引用、数据源绑定等均依赖「数据项名 → 值」的读写。第一层数据项名（功能 4.4.1）指文档顶层区域/数据组的**数据项名**列表，用于导航、续打参数、质控段列表等。

#### 6.7.2 阶段 2：结构化的持久化

- **区域、数据组、数据元均不单独建表**；其**结构定义与实例数据**均存在于**文档或模板的 content（JSON）** 中，作为 Tiptap 自定义节点的树形结构。
- **持久化形态**：`emr_document.content` / `emr_template.content` 存完整 ProseMirror JSON，其中包含所有 region/section/dataElement 节点及其 attrs（id、**数据项名** name、title、type、value、必填、参与打印等）。
- **按数据项名读写**：服务端或前端遍历 content JSON，根据**数据项名**（`attrs.name` 或 `attrs.id`）定位节点并读写 value；批量赋值接口传入「数据项名 → value」映射，服务端解析 content 后写回对应节点再落库。
- **数据项名列表（不打开文档）**：服务端解析 content JSON 提取区域/数据组/数据元的**数据项名**列表、块→页号等，无需独立「结构表」。若需**加速按数据项名检索或统计**（如按「血常规」查文书），可将**数据项名**单独持久化：例如表 `emr_document_data_item_index`（document_id、node_type、**数据项名**、可选 result_id 等），在保存文档时解析 content 写入；详见 6.6 存储建议。

#### 6.7.3 阶段 3：模板与模式的业务含义

| 概念 | 业务含义 | 在 EMR 中的用途 |
|------|----------|-----------------|
| **模板（Template）** | 某类文书的**标准结构**：预置好的区域、数据组、数据元（含**数据项名**、类型、必填等），内容可为空或默认值。 | 新建文书时「从模板新建」即复制模板 content 作为文档初值；保证同类文书结构一致，便于质控与解析。 |
| **书写模式** | 仅允许在**数据元内填写**，禁止增删改区域/数据组结构（禁止删块、禁止插入块级节点）。 | 防止医生误删「现病史」「体格检查」等段落，保证文书与模板结构一致；模板编辑时则允许自由编辑结构。 |
| **复制粘贴策略** | 书写模式下粘贴仅**纯文本**或受控类型；**防跨患者**：粘贴内容携带来源患者 ID，与当前患者一致才允许粘贴。 | 避免从其他患者文书整段拷贝导致串患者；符合合规与质控要求。 |

**文书类型与默认模板**：文书类型（如入院记录、病程记录、出院小结）在 `emr_document_type` 配置；可绑定默认模板 id，新建时若不选模板则用该默认模板 content 初始化。

#### 6.7.4 阶段 3：模板与模式的持久化

| 内容 | 持久化方式 |
|------|------------|
| **模板** | **emr_template** 表：id、名称、编码、**content**（完整 JSON，含区域/数据组/数据元及**数据项名**）、启用、审计字段（与 BaseAuditedEntity 一致）。模板列表、按 ID 取 content 供「从模板新建」与模板管理。 |
| **文书类型与默认模板** | **emr_document_type** 表：编码、名称、**default_template_id**（外键，可选）、启用。新建文档时若传入文书类型且未传模板 id，则用 default_template_id 对应模板的 content 初始化。 |
| **书写模式** | **不单独持久化**。由前端根据「当前打开的是模板还是文书」决定：打开模板且为「编辑模板」则允许编辑结构；打开文书则为书写模式（schema 限制或只读 + 数据元可编辑）。可选：在文档或会话中存 `is_template_edit` 等标识，若需服务端区分则文档表可增加 **is_template**（布尔）区分模板与实例文书，或由文书类型推断。 |
| **复制粘贴 / 防跨患者** | **策略不落库**或仅配置项：如「是否启用防跨患者校验」可放系统配置/字典；粘贴内容中的来源患者 ID 由前端在复制时写入剪贴板数据，保存时服务端可校验。 |

综上：阶段 2 的持久化 = 文档/模板的 **content 字段**；阶段 3 的模板与文书类型 = **emr_template**、**emr_document_type** 表及 default_template_id 关联；书写模式与粘贴策略以前端策略为主，必要时辅以配置或文档标识。

## 九、关键设计决策

| 决策项 | 结论 | 说明 |
|--------|------|------|
| **文档存储格式** | 以 Tiptap/ProseMirror JSON 为唯一存储与交换格式 | 便于版本 diff、服务端解析结构、OpenPDF 渲染时一致解析 |
| **按数据项名取值/赋值** | 区域/数据组/数据元均支持**数据项名**（`attrs.name` 或 `attrs.id`）；批量赋值由接口传「数据项名 → value」映射，服务端或前端遍历 JSON 写回 | 支持诊断带入、检查检验引用、数据源绑定等 |
| **书写模式** | Schema 限制（禁止删除块级结构）或只读 + 数据元 NodeView 内 editable | 保证模板结构不被误删改 |
| **打印与续打** | 全部由服务端 OpenPDF 完成；续打 = 生成「从第 N 页起」或「仅指定块/区域」的 PDF；前端仅传参数与 content | 不依赖浏览器打印；静默打印由客户端配合 PDF 流 |
| **打印预览** | L1 编辑区 + L2 OpenPDF 权威预览共用同一渲染器；previewMode 区分预览与正式打印 | 详见《打印预览设计》§二、§五 |
| **留痕** | 前端 Tiptap 扩展（track changes 类 mark）或服务端保存时 diff 生成带 mark JSON；版本快照与痕迹元数据在服务端 | 兼顾编辑时体验与合规可追溯 |
| **不打开文档解析** | 服务端解析文档 JSON 提取**数据项名**列表、按属性过滤、块→页号；不依赖前端打开编辑器 | 支持列表展示、检索、续打参数、质控等 |
| **校验** | 保存前以服务端统一校验为主，返回错误列表；前端可做轻量预校验以提升体验 | 必填、长度、逻辑、违禁字、结构合法性 |
| **裁剪** | OFD 暂不实现；静默打印仅提供 PDF 流；多语言按需 | 见功能清单 1.3 |
| **12.1 HIS 患者/就诊** | 仅对接 **patientId、encounterId**；患者/就诊列表由医生站或 zxplat-domain 承担 | EMR 文书与元数据按 ID 关联；见功能清单 §1.4、V14.2 |

## 十、安全与合规要点

| 项 | 说明 |
|------|------|
| **传输** | HTTPS；文档 JSON 与 PDF 流经 TLS 传输。 |
