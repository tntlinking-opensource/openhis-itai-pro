## 一、信息架构与导航

### 1.1 菜单结构

```text
收费工作站 ChargeStation（一级 · health V1 既有，parent_id 310400000000000001）
└── 电子发票 EinvoiceBossHub（二级目录，remark: module_id=einvoice-boss）
    ├── 待补偿开票      → /finance/einvoice/compensation     P0  ★默认落地页
    ├── 电子发票查询    → /finance/einvoice/list             P1
    ├── 收费对照维护    → /finance/einvoice/contrast         P2
    ├── 财务日结核对    → /finance/einvoice/reconcile        P2
    └── 通用票开具      → /finance/einvoice/common           P3

门诊收费 / 挂号 / 住院结算（health 既有页面 · 嵌入组件，非新菜单）
├── 收费成功区          → EinvoiceIssueStatusPanel（当前 mainly 住院结算页）
└── 账单详情            → 金额不一致 Banner（health 增强）    P1
```

> **说明**：Flyway 种子（`einvoice_boss/V2__EinvoiceBoss_Seed.sql`）将「电子发票」挂在 **收费工作站** 下，**不是**「财务管理」一级。可见性还需角色具备 `einvoice-boss.*` 权限（种子默认授权 admin、财务 accountant）。

### 1.2 路由与 API 对照

| 路由 / 组件 | 页面/用途 | API 前缀 |
| --- | --- | --- |
| `/finance/einvoice/compensation` | 待补偿开票列表 | `GET/POST /api/einvoice-boss/tasks/*` |
| `/finance/einvoice/list` | 电子发票查询 | `GET /api/einvoice-boss/documents/page` |
| `/finance/einvoice/document/:id/amount` | 金额调整 | `GET/PUT/POST /api/einvoice-boss/documents/*` |
| `EinvoiceIssueStatusPanel` | 收费窗开票进度 | `GET /api/einvoice-boss/issue-status` |
| `EinvoiceQrPanel` | 收费窗二维码 | `GET /api/einvoice-boss/cashier/qr` |
| 全局角标/顶栏 | 待补偿统计 | `GET /api/einvoice-boss/tasks/pending-compensation?countOnly=true` |

### 1.3 角色与权限（建议）

| 权限码 | 说明 | 角色 |
| --- | --- | --- |
| `einvoice-boss.compensation.view` | 看待补偿列表 | 财务、收费班长 |
| `einvoice-boss.compensation.operate` | 重新入队/立即开具/busNo 补偿 | 财务、收费班长 |
| `einvoice-boss.document.adjust` | 金额调整页编辑保存 | 财务 |
| `einvoice-boss.document.view` | 查询列表、查看 QR | 财务、收费员 |
| `einvoice-boss.cashier.qr` | 收费窗 QR/进度 | 挂号员、收费员 |

### 1.4 核心用户路径

| 路径 | 角色 | 阶段 |
| --- | --- | --- |
| 收费完成 → 见「开票中」→ 轮询出 QR | 收费员 | P1 |
| 登录见顶栏提醒 → 待补偿列表 → 重新入队 | 收费班长 | P0 |
| 待补偿「金额待调整」→ 金额页调额 → 重新开具 | 财务 | P1 |
| 账单金额不一致 → 微调账单 → 查看电子发票 → 调额重开 | 收费员/财务 | P1 |
| 超时待查 → busNo 补偿 → 确认已开具 | 财务 | P0 |

## 二、全局提醒（P0 · 必做）

### 2.1 菜单角标

| 位置 | 行为 |
| --- | --- |
| 「收费工作站 → 电子发票」或顶栏待补偿入口 | `pendingCount > 0` 时显示红色数字角标 |
| 刷新时机 | 登录后、路由切换回财务模块、待补偿操作成功后 |

### 2.2 顶栏 Alert

**显示条件**：`pendingCount >= einvoice.boss.compensation.alertThreshold`（默认 1）

**线框：**

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ ⚠ 有 3 笔电子发票待补偿开票，可能影响患者取票，请尽快处理。  [去处理] [今日不再提示] │
└──────────────────────────────────────────────────────────────────────────────┘
```

| 元素 | 说明 |
| --- | --- |
| 类型 | `el-alert`，`type=warning`，`show-icon`，可关闭 |
| 文案 | **固定**：「有 {n} 笔电子发票待补偿开票，可能影响患者取票，请尽快处理。」 |
| [去处理] | 跳转 `/finance/einvoice/compensation` |
| [今日不再提示] | `localStorage` 记当日日期，当天不再弹（角标仍保留） |

**权限**：有 `einvoice-boss.compensation.view` 的用户可见。

## 三、待补偿开票（P0）

- **路由**：`/finance/einvoice/compensation`
- **用途**：事件丢失、开票失败、超时未开具的集中处理入口。

### 3.1 布局线框

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ 待补偿开票                                                                    │
│ 待处理 3 笔  │  事件丢失 1  │  金额待调整 1  │  开票失败 0  │  超时待查 1      │
├──────────────────────────────────────────────────────────────────────────────┤
│ 筛选：日期范围 [____]  患者姓名/就诊号 [____]  异常类型▼  业务线▼  [查询][重置] │
├──────────────────────────────────────────────────────────────────────────────┤
│ 患者   │ 就诊号  │ 业务线 │ 支付金额 │ busNo      │ 异常类型   │ 等待时长 │ 操作 │
├────────┼─────────┼────────┼──────────┼────────────┼────────────┼──────────┼──────┤
│ 张三   │ MZ001   │ 门诊   │ 128.50   │ INV2026…   │ [金额待调整]│ 12分钟   │ ···  │
│ 李四   │ GH002   │ 挂号   │  15.00   │ INV2026…   │ [事件丢失] │  2分钟   │ ···  │
│ 王五   │ MZ003   │ 门诊   │  56.00   │ INV2026…   │ [超时待查] │ 45分钟   │ ···  │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 异常类型标签

| 后端条件 | 标签文案 | Tag 颜色 | 主操作 |
| --- | --- | --- | --- |
| DRAFT + 无 task | 事件丢失 | `danger` | 重新入队 |
| task=FAILED + `AMOUNT_MISMATCH` | 金额待调整 | `warning` | 调整金额 |
| task=FAILED + 其他 | 开票失败 | `danger` | 立即开具 |
| DRAFT 超 `staleMinutes` 未 ISSUED | 超时待查 | `info` | 流水号查票 |

### 3.3 行操作菜单

| 操作 | 显示条件 | API | 权限 |
| --- | --- | --- | --- |
| **重新入队** | 事件丢失 / 开票失败 | `POST .../tasks/{invoiceId}/requeue` | operate |
| **立即开具** | 开票失败 / 金额已调整后 | `POST .../tasks/{invoiceId}/issue-now` | operate |
| **流水号查票** | 超时待查 / 开票失败 | `POST .../tasks/{invoiceId}/recover-by-busno` | operate |
| **调整金额** | 金额待调整 | 跳转金额页 | adjust |
| **查看详情** | 始终 | 抽屉：document + task + 最近日志 | view |

### 3.4 确认弹窗文案（固定）

#### 立即开具

```text
标题：确认立即开具
正文：将向博思平台发起电子票据开具。
      · 请确认金额已在「电子发票金额」页核对无误。
      · 若博思侧已存在同流水号票据，重复操作可能导致异常。
      [取消]  [确认开具]
```

#### 流水号查票补偿

```text
标题：确认流水号查票
正文：将使用业务流水号 {busNo} 向博思查询开票结果。
      · 若博思已开票，系统将直接标记为已开具并回写票号。
      · 若未开票，请改用「重新入队」或「立即开具」。
      [取消]  [确认查询]
```

#### 重新入队

```text
标题：确认重新入队
正文：将重新加入后台开票队列，不会立即调用博思。
      [取消]  [确认]
```

### 3.5 操作反馈

| 结果 | UI |
| --- | --- |
| 成功 | Toast「操作已提交」；行状态刷新；`pendingCount` 减 1 |
| 失败 | Toast 展示 `last_error_msg`；行内展示错误摘要 |
| 查票已存在 | Toast「已查回票面，票号 {billNo}」；该行移出列表 |

### 3.6 空状态

```text
暂无待补偿开票记录
后台开票正常时，患者可在收费窗扫码取票。
```

## 四、电子发票金额调整（P1）

- **路由**：`/finance/einvoice/document/:documentId/amount`
- **入口**：待补偿列表「调整金额」、查询列表「调额」、账单页链接。

### 4.1 布局线框

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ ← 返回   电子发票金额调整                              状态 [金额不一致] warning │
├──────────────────────────────────────────────────────────────────────────────┤
│ 概要                                                                        │
│  患者：张三（男，45岁）    就诊号：MZ20260618001    业务线：门诊收费            │
│  支付单号：PAY-xxx         业务流水号 busNo：INV20260618000123                │
│  支付金额（只读）：128.50    开票总额 [ 128.50 ]    差额：0.00 ✓              │
├──────────────────────────────────────────────────────────────────────────────┤
│ 明细                                                    [校验金额] [+ 调平行] │
│ ┌────┬──────────────┬──────────┬──────────┬────┬─────────────────────────┐ │
│ │ 行 │ 项目名称      │ 标准金额  │ 出站金额  │ 单位│ 备注                     │ │
│ ├────┼──────────────┼──────────┼──────────┼────┼─────────────────────────┤ │
│ │ 1  │ 诊察费        │  50.00   │ [ 50.00] │ 次 │                          │ │
│ │ 2  │ 化验费        │  78.50   │ [ 78.00] │ 次 │ 已调整                    │ │
│ ├────┴──────────────┴──────────┴──────────┴────┴─────────────────────────┤ │
│ │ 合计                              128.00   ← 与开票总额不等时红色高亮      │ │
│ └──────────────────────────────────────────────────────────────────────────┘ │
├──────────────────────────────────────────────────────────────────────────────┤
│ 调整原因（必填） [________________________________________________]            │
│                                    [保存调整]  [重新开具]  [取消]             │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 4.2 字段与校验

| 字段 | 可编辑 | 规则 |
| --- | --- | --- |
| 支付金额 | 否 | 来自 payment 快照 |
| 开票总额 `total_amt` | 是 | 默认 = adm_invoice.amount |
| 出站金额 `amount` | 是 | 改后行标记「已调整」 |
| 标准金额 `std_amount` | 否 | 灰色展示，对比用 |
| 调整原因 | 是 | 保存前必填，≥5 字 |

**客户端预校验**（点击「校验金额」或「保存」）：

```text
sum(出站金额) 必须等于 开票总额
否则：表单项标红 + 文案「明细合计 {sum} 与开票总额 {total} 相差 {diff} 元」
```

**服务端**：`POST /documents/{id}/validate-amount` 返回 `{ valid, lineSum, totalAmt, diff }`；`PUT` 保存时再次校验，失败禁止入库。

### 4.3 金额状态展示

| amount_status | 页头标签 |
| --- | --- |
| MATCH | 金额一致（success） |
| MISMATCH | 金额不一致（warning） |
| ADJUSTED | 已人工调整（info） |

### 4.4 「重新开具」交互

1. 若未保存且明细有改动 → 弹窗「请先保存调整」
2. 若校验未通过 → 禁止点击
3. 通过后走 §3.4「立即开具」确认弹窗 → `issue-now`
4. 成功 → Toast + 可选跳转查询列表查看 QR

### 4.5 「调平行」（可选快捷）

当差额为小数尾差（如 0.01）时，允许一键新增一行「金额调平」：

- 名称固定「金额调平」
- 金额 = `total_amt - sum(其他行)`
- 自动填调整原因前缀「尾差调平」

## 六、收费窗嵌入组件（P1）

挂载于 **门诊收费结算成功**、**挂号缴费成功** 结果区（health 页面不改主流程，仅嵌入）。

### 6.1 `EinvoiceIssueStatusPanel`

**线框（结算成功卡片内）：**

```text
┌─ 电子发票 ─────────────────────────────────────┐
│  ○ 开票中…        （DRAFT + task 进行中）       │
│  ✓ 已开具         票号 00123456  [查看二维码]    │
│  ⚠ 开票失败       请联系财务处理  [查看原因]     │
└────────────────────────────────────────────────┘
```

| invoiceStatus + task | 展示 | 行为 |
| --- | --- | --- |
| DRAFT，无 task / PENDING | 「开票中…」+ 小菊花 | 每 3s 轮询 `issue-status`，最多 2min |
| DRAFT，FAILED | 「开票失败」+ 原因摘要 | [查看原因] 跳转待补偿（无权限则仅 Tooltip） |
| ISSUED | 「已开具」+ 票号 | 展示 `EinvoiceQrPanel` |
| 轮询超时仍 DRAFT | 「开票较慢，请稍后扫码或联系收费处」 | 停止轮询，保留手动刷新按钮 |

**文案原则**：支付已成功**始终**先展示；不出现「开票失败请重新缴费」类表述。

### 6.2 `EinvoiceQrPanel`

| 状态 | 展示 |
| --- | --- |
| ISSUED | QR 图 + 「请患者扫码查看电子发票」 |
| 非 ISSUED | 灰色占位图 + 「二维码生成中」 |

API：`GET /api/einvoice-boss/cashier/qr?paymentId=`

## 七、账单页协同（health · P1）

**页面**：门诊账单详情 / 住院账单详情（health 团队实现，boss 仅提供跳转参数约定）。

### 7.1 不一致 Banner

**显示条件**：`sum(chargeItems) ≠ payment.amount`

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ ⚠ 账单明细合计 {itemSum} 元，与支付金额 {payAmt} 元不一致，请微调后再开票。      │
│   [去微调账单]    [查看电子发票]                                               │
└──────────────────────────────────────────────────────────────────────────────┘
```

| 按钮 | 行为 |
| --- | --- |
| 去微调账单 | 停留当前页，聚焦可编辑明细行（health 既有能力） |
| 查看电子发票 | 若已有 documentId → `/finance/einvoice/document/{id}/amount`；否则 Toast「电子发票尚未生成」 |

### 7.2 微调后

保存账单成功后：Toast「账单已更新，后台将重新尝试开票」；若 boss 模块启用，可调用 `requeue`（可选 P1+，默认依赖 Worker 下次扫描）。
