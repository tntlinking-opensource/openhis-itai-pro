# 门诊日结与医保退费缺陷 · 问题与修改方案

> **日期**：2026-07-27  
> **环境**：`（院点训练库，历史记录）`（院点 H22010402403）  
> **关联**：AS-OP-FIN-004 门诊日结 · AS-OP-FIN-003 门诊退费 · CHS 2207/2208 · [#11 日结缺陷](./28-医保联调缺陷-修复方案-2026-07-27.md)

## 1. 现象

门诊日结查询（IF-OP-DCL-02）出现：

| 项 | 值 | 异常 |
|----|-----|------|
| 总收入 | 8.01（西药 6.01 + 诊察 2.00） | 已退费用仍计入上半区 |
| 微信 | 5.00 | 与总收入/医保不对账 |
| 市区医保账户 | **-5.01** | 应为净 0 或仅有效结算 |
| 市区医保总额 | **-5.01** | 同上 |
| 市医保人次 | 2 | 含冲销后样本 |

**结论**：前端日结页基本原样展示后端 `summary`，**-5.01 非前端重算错误**；为多条写路径缺陷 + 日结读侧放大叠加。

## 2. training 关键证据（2026-07-27）

### 2.1 对上 -5.01 的支付链

| payment_no | 角色 | status / payment_enum | 个账明细 | 桥表 | 分类快照 |
|------------|------|----------------------|----------|------|----------|
| `…026` | 有效市医保 | SUCCESS / PAY | +1.00 | **CONFIRMED** | 诊察 1.00 |
| `…021` | 已冲销原单 | SUCCESS / PAY | +1.00 | **REVOKED** | 诊察 1.00 |
| `…024` | 021 逆向 | REFUNDED / UN_PAY | **无** | 无 | **0** |
| `…027` | 已冲销原单 | SUCCESS / **CASHIER** | +6.01 | **REVOKED** | 西药 6.01 |
| `…028` | 027 逆向 | REFUNDED / UN_PAY | +6.01（`pay_trans_no` 空） | **无** | **0** |

日结医保桶现行算法：

- `026` 计入 **+1.00**
- `027` 桥表 REVOKED → **不计入**
- `028` 无桥表 → 兼容为可计 → 取负后 **-6.01**
- 合计：**1 − 6.01 = −5.01**（与截图一致）

总收入 8.01：诊察 1+1 + 西药 6.01；两笔逆向快照均为 0，**未冲掉原单分类金额**。

### 2.2 同态检查（正常项）

| 检查 | 结果 |
|------|------|
| `fin_payment_yb_settlement.status` vs `yb_settlement_record.status` | 一致（#11-C 写路径有效） |
| `yb_settlement_record` 有 payment 无桥表 | 0（正向结算） |
| 一笔 payment 多桥表行 | 0（今日样本） |

## 3. 根因：多 BUG 清单

### BUG-1 · 日结读侧：REVOKED 单边剔除（高）

| 项 | 内容 |
|----|------|
| **落点** | `OutpatientDailySettlementMapperImpl#shouldCountInsuranceDetail` / `accumulateContractPaymentSummary`；住院 `InpatientDailySettlementMapperImpl` 对称 |
| **机制** | 原单桥表全部 `REVOKED` 或 `pay_trans_no` 命中已撤 setl → 个账/统筹不计；逆向 `UN_PAY` 常无桥表 → 空桥表兼容为「可计」→ 带符号负数仍计入 |
| **后果** | 收费→2208→退费后，市/省医保账户虚减；与 #11-C「冲销后不计」验收未覆盖「成对退费」 |
| **前端** | `views/outpatient/charge/daily-settlement/index.vue` 仅展示 `municipalInsuranceAccount`，无二次计算 |

### BUG-2 · 退费写侧：逆向医保关联不完整（高）

| 项 | 内容 |
|----|------|
| **落点** | `OutpatientRefundMapperImpl#toPaymentDetailItemCommands`；`#toCompleteOutpatientRefundCommand`；`OutpatientRefundAppService#execute…` |
| **机制** | ① 明细只拷 `payEnum`+`amount`，**不拷 `pay_trans_no`**；② 完成命令**不设 `ybSettlements`** → 逆向无 `fin_payment_yb_settlement`；③ 退费前 2208 只把**原单**桥表标 REVOKED |
| **后果** | 喂给 BUG-1；日结无法用 setl 行级对齐 |
| **前端** | `charge/refund/index.vue` 不传 setl（合理）；期望后端从原单补全 |

### BUG-3 · 退费写侧：分类快照金额为 0（高）

| 项 | 内容 |
|----|------|
| **落点** | `PaymentFinTypeStaticSnapshotListener` → `PaymentFinTypeStaticSnapshotWriter#writeForPayment`（`OutpatientRefundCompletedEvent`） |
| **机制** | 逆向单 `displayAmount`/`tenderedAmount` 常为 0（医保全个账）；快照写入后 `fin_payment_rec_static.amount=0`，无法与原单正数抵净 |
| **后果** | 上半区总收入虚高（已退西药/诊察仍在）；与下半区支付渠道对不上 |
| **证据** | `…027` static=6.01，`…028` static=0；`…021`/`…024` 同理 |

### BUG-4 · 收费写侧：`payment_enum` 误用渠道码（中）

| 项 | 内容 |
|----|------|
| **落点** | `OutpatientChargeMapperImpl#toCreatePaymentDraftFromPreSettleCommand`：`setPaymentEnum(PaymentChannel.CASHIER.getCode())`；`PaymentReconciliationDomainService#settleOutpatientPayment` 只改 status，不改 payment_enum |
| **机制** | `payment_enum` 语义为 `PaymentType`（`PAY`/`UN_PAY`），误写入渠道 `CASHIER`；正式结算后残留 |
| **后果** | training `…027`：SUCCESS + 有医保结算，头字段仍为 `CASHIER`；凡按 `PAY` 过滤的读路径会漏单 |
| **日结影响** | 逆向判定主要靠 `relation_id`/`UN_PAY`，本条暂未直接导致 -5.01 |

### BUG-5 · 前端展示：现金字段绑错（低）

| 项 | 内容 |
|----|------|
| **落点** | `api/outpatient/daily-settlement.ts` → `DAILY_SETTLEMENT_SUMMARY_DISPLAY` |
| **机制** | 标签「现金」绑定 `selfPayCashTotal`（自费桶现金）；后端另有全渠道 `cashAmount` 未展示 |
| **后果** | 展示语义易误解；非 -5.01 主因 |

## 5. 修改方案

### 5.1 原则

1. **成对语义**：原单 SUCCESS + 逆向 UN_PAY 在日结窗内，医保个账/统筹与 fin_type **代数和应为 0**（一收一退抵净，BR-OP-DCL-011）。
2. **冲销 alone**：仅 2208、无本地 UN_PAY 时，原单医保渠道仍可不计（保留 #11-C 防虚增）。
3. **写全再读**：优先补全退费写路径，再收紧读侧兼容分支。
4. **门/住院对称**：住院日结 Mapper 同步改。

### 5.2 BUG-1 修改方案（日结读侧）

**推荐（与成对退费兼容）**：

在 `shouldCountInsuranceDetail` / 医保渠道累加前增加：

| 步骤 | 动作 |
|------|------|
| 1 | 若当前 payment 为逆向（`relation_id` 非空或 `UN_PAY`）：加载原单桥表（批量预载，禁 N+1） |
| 2 | 若原单对应 setl（或原单全部桥表）为 `REVOKED`：**逆向医保 fund/acct 也不计** |
| 3 | 若明细 `pay_trans_no` 能匹配原单已撤 setl：同样不计 |
| 4 | 空桥表兼容仅保留给「历史无桥表的正向单」；**逆向空桥表默认不计医保渠道**（或必须能关联到原单 CONFIRMED） |

**备选（更简单、改动面大）**：取消对 REVOKED 原单的单边剔除，一律正负都计、靠代数和抵净。须回归「只冲销不退费」样本，避免虚增。

**验收**：

- [ ] `…027`+`…028` 成对后，市医保账户净额 **0**（在无其它有效市医保时）
- [ ] 仅有 `…026` CONFIRMED 时，市医保账户 **+1.00**
- [ ] 仅 2208、无 UN_PAY 的冲销样本，个账仍不进日结（#11-C）

### 5.3 BUG-2 修改方案（退费写侧）

| 步骤 | 落点 | 动作 |
|------|------|------|
| 1 | `toPaymentDetailItemCommands` + 装配处 | 从原支付明细按渠道拷贝 `pay_trans_no`（及必要的 `result_enum`）；医保行必须带原 `setl_id` |
| 2 | `toCompleteOutpatientRefundCommand` / execute | 按原单 `fin_payment_yb_settlement` 生成逆向侧桥表行：`setl_id` 同原、`status=REVOKED`（或与产品约定「逆向不建桥、读侧只认原单」——若选后者须与 BUG-1 方案强制一致） |
| 3 | 明细 `result_enum` | 收口为成功/已退语义，禁止终态仍为 `DRAFT` |

**推荐写约定**：逆向也落桥表一行（`REVOKED` + 同 `setl_id` + `settlement_record_id`），与原单同态，日结行级过滤简单。

**验收**：

- [ ] 新退费样本：逆向 `INSURANCE_*` 行 `pay_trans_no = 原 setl_id`
- [ ] 逆向存在桥表且 status 与业务约定一致
- [ ] 不再依赖「空桥表兼容」才能解释退费单

### 5.4 BUG-3 修改方案（退费分类快照）

| 步骤 | 落点 | 动作 |
|------|------|------|
| 1 | `PaymentFinTypeStaticSnapshotWriter` | UN_PAY / 退费完成：分摊基数 = Σ\|关联 charge_item.total_price\|（与正向一致）；**禁止**因 header display/tendered=0 写出全 0 |
| 2 | 若 charge_item 已 REFUNDED 仍保留原 total_price | 继续用绝对值（training 已证实 REFUNDED 行 price 仍在） |
| 3 | 历史 | 对今日 `…024`/`…028` 等 static=0 的逆向单跑 `writeForPayment` 重建 |

**验收**：

- [ ] 新退费：逆向 static 金额绝对值 = 原单对应分类合计
- [ ] 同日窗一收一退后，上半区对应 fin_type 代数和为 0

### 5.5 BUG-4 修改方案（payment_enum）

| 步骤 | 落点 | 动作 |
|------|------|------|
| 1 | `OutpatientChargeMapperImpl` 建草稿 | `setPaymentEnum(PaymentType.PAY.getCode())`，**禁止**写入 `PaymentChannel.CASHIER` |
| 2 | `settleOutpatientPayment` | 防御：若仍为 `CASHIER`/非法值，收口为 `PAY` |
| 3 | 历史 | training 中 SUCCESS+CASHIER 批更 `PAY`（可选） |

**验收**：新收费落账 `payment_enum=PAY`；退费逆向 `UN_PAY`。

### 5.6 BUG-5 修改方案（前端展示）

| 步骤 | 落点 | 动作 |
|------|------|------|
| 1 | `DAILY_SETTLEMENT_SUMMARY_DISPLAY` | 「现金」改为绑定 `cashAmount`，或标签改为「自费现金」并与产品确认老日结单口径 |
| 2 | 与 AS-OP-FIN-004 / 打印模板对齐后改一处、打印同步 |

## 8. 明确不做（本期）

- 废弃 `fin_payment_yb_settlement`、把头上扩单字段 `yb_settle_id`（支付:结算为 1:N，见既有结论）
- 用 `yb_settlement_record` 金额直接替换日结渠道汇总（仍以 `fin_payment_rec_detail` 为院内记账权威）
- 改正式库历史全量洗数（仅 training 抽检 + 新单验证）
