### 0.3 F1 · 归档组件（选且仅选一项）

| 代号 | 组件 | 是什么 | 利 | 弊 | 单独能否支撑 DICOM Web | 运维 |
|------|------|--------|----|----|------------------------|------|
| **A1** | **Orthanc 单节点** | 轻量 DICOM 服务 + DICOMweb | 部署快；与多数 Web Viewer 资料多；C-STORE/QIDO/WADO 齐 | GPLv3（独立进程）；单机扩展弱；企业审计/多租户弱 | ✅ | 低 |
| **A2** | **Orthanc 集群/复制** | 多节点 + 共享盘/replication | 比 A1 高可用 | 配置与排障成本升 | ✅ | 中 |
| **A3** | **dcm4chee-arc** | 成熟开源档案 | 多院区、权限、HL7、审计更「院级」 | 部署重；首版联调慢 | ✅ | 高 |
| **A4** | **MinIO/S3 + STOW/自研索引** | 对象桶存 DCM | 与对象存储统一 | 缺原生 C-STORE；须另做 DICOMweb 网关才能接标准 Viewer | ⚠️ 须补网关 | 中高 |
| **A5** | **仅本地文件系统** | 目录落文件，无 DICOM 服务 | 零中间件 | 无标准阅片源；设备直连难 | ❌ 不可作归档定稿 | 极低 |
| **A6** | **商业 VNA/厂商归档** | 采购归档，ZXPlat 接协议 | 合规/质控外包；认可度高 | 采购周期与费用；接口各异 | ✅（若提供 Web/DICOMweb） | 低（外包） |
| **A7** | **遗留 WebPacs/wpacs** | 续用旧库与旧入口 | 现场熟；迁移动作小 | 技术债；难标准化；双栈长期痛 | ⚠️ 取决于旧系统 | 中 |

**禁止单独定稿**：A5。  
**参考（非强制）**：单院区、要快 → 倾向 A1；明确多院区/强审计 → 倾向 A3。

#### F1 若选 A1：以后接到多院区怎么办？

> 结论：**国基首版选 A1 不妨碍**后续多院区；多院区用「同协议换部署/换产品」，而不是推翻 RIS。前提是 ZXPlat 始终只依赖 **DICOMweb（或适配器端口）+ StudyUID**，不把 Orthanc 私有 API 写进 Domain。

| 演进档 | 做法 | 何时用 | 对 ZXPlat 的改动 | 利 | 弊 |
|--------|------|--------|-----------------|----|----|
| **E1 单院加机器** | 仍 Orthanc，加大盘/垂直扩容 | 单院量涨、仍单院区 | 几乎无 | 成本最低 | 到顶仍是单归档 |
| **E2 升 A2** | Orthanc 复制/共享存储集群 | 要高可用，仍认 Orthanc | 运维为主；adapter 地址改配置 | 产品形态不变 | 运维复杂度升 |
| **E3 一院区一 Orthanc** | 每院区一套 A1，ZXPlat 按 `orgId`/院区路由归档端点 | 医共体、多院区但体量中等 | **imaging 配置多端点**（IM-CFG 类）；Study 记录带 `archiveNodeId` | 隔离好、故障域小 | 跨院区调阅要路由/网关；运维 N 套 |
| **E4 中心索引 + 边缘归档** | 边缘 C-STORE 收图，中心做查询/冷存（仍可 Orthanc 或对象存储） | 多院区要统一检索 | adapter 增加「路由 + 汇总查询」 | 扩展清晰 | 设计量明显大于 E3 |
| **E5 该院点换 A3/A6** | 新项目/新租户定稿 dcm4chee 或商业 VNA；国基可继续 A1 | 甲方点名院级档案/已有 VNA | **新 adapter 实现**同一端口；`pacs_viewer_endpoint` / 归档 baseUrl 按机构配置 | 产品可多归档并存 | 要维护多实现；测试矩阵变大 |
| **E6 全产品迁出 Orthanc** | 所有院点迁到 A3/A6 | Orthanc 全面不够 | 迁移工具 + 双跑期 | 长期统一 | 贵、久；**首版不必预支** |

**多院区项目到来时的决策树（简）**

```text
新项目多院区？
  ├─ 仍接受 Orthanc 运维能力 → E3（一院一节点）或 E2/E4
  ├─ 要强审计/HL7/院级 VNA 叙事 → 该租户 E5=A3 或 A6（国基可仍 A1）
  └─ 已有集团 VNA → E5=A6，ZXPlat 只接 DICOMweb/厂商协议
```

**首版选 A1 时必须守住的工程约束（否则多院区会痛）**

1. Domain 只存 StudyUID / 归档节点 ID / 业务外键，**不**写 Orthanc 内部 ID 当唯一真源以外的耦合。  
2. `module-pacs-imaging-application（Orthanc/MinIO 端口）` 出端口：`DicomIngress`、`DicomWebQuery`、`ViewerUrl` —— Orthanc 只是**实现之一**。  
3. 机构级配置：归档 baseUrl、AE Title、阅片 URL 模板均可按院区覆盖。  
4. 不要在报告/核心 RIS 里写死 `http://orthanc:8042`。

**和「首版直接选 A3」的对比**

| | 首版 A1，多院区再演进 | 首版直接 A3 |
|--|----------------------|-------------|
| 国基上线速度 | 快 | 慢 |
| 多院区到来时成本 | 一次适配/扩部署（E3～E5） | 首版已偏重，多院区少一次选型争论 |
| 风险 | 若把 Orthanc API 写进业务，演进成本暴涨 | 首版过重、可能过度设计 |

→ **国基已选定 F1=A1**（2026-09-21）。多院区按上表 **E3/E5** 演进，不推翻本项。

### 0.4 F2 · 阅片组件（选且仅选一项）

| 代号 | 组件 | 是什么 | 利 | 弊 | 能否算 C7「DICOM Web 阅片」 | 对接方式 |
|------|------|--------|----|----|------------------------------|----------|
| **V1** | **OHIF Viewer v3** | 浏览器阅片 | MIT；DICOMweb 原生；iframe 友好；示例多 | 深度不如顶级商业；需配 appConfig | ✅ | URL + Token |
| **V2** | **Orthanc Web（Explorer 2 / Stone）** | Orthanc 插件阅片 | 少维护一套独立前端 | 体验/生态不如 OHIF；**强依赖 F1=A1/A2** | ✅ | Orthanc URL |
| **V3** | **Weasis** | 开源桌面/可 Web 启动 | 放射科桌面习惯好；功能全 | 安装/分发成本；「纯 Web」叙事弱 | ⚠️ 须院方书面认 Web | 协议唤醒/下载 |
| **V4** | **商业 Web Viewer** | 只配启动 URL | ZXPlat 工作量最小；医生认可度高 | 依赖采购；无合同则堵死 | ✅ | endpoint 模板 |
| **V5** | **自研 Cornerstone 页** | ZXPlat 自拼阅片 UI | 品牌一体 | **踩禁止项**；人年坑 | — | — |
| **V6** | **仅关键图灯箱** | 只看 JPEG/PNG | 极快 | **不过 C7** | ❌ | Media URL |

**禁止定稿**：V5；V6（不可当作 DICOM Web 阅片）。  
**前提**：F1 已锁 **A1**，故 **V2 可用**；V1/V3/V4 也都能接 Orthanc DICOMweb。

#### 在 F1=A1 下，F2 怎么比

真正要在 **V1 与 V2** 之间选。V3、V4 只在「院方认桌面」或「已有采购」时成立。

| 代号 | 组件 | 和 Orthanc 怎么接 | 利（相对 A1） | 弊（相对 A1） | 换归档时（E5） |
|------|------|-------------------|---------------|---------------|----------------|
| **V1** | **OHIF v3** | Orthanc 开 DICOMweb；OHIF `appConfig` 指 QIDO/WADO；ZXPlat 拼 StudyUID URL + Token | 浏览器内嵌最成熟；测量/序列/多窗资料多；**阅片与归档解耦**（以后换 dcm4chee 只改数据源） | 多维护一个前端容器与版本；要配数据源和鉴权反代，避免 Orthanc 裸奔 | 阅片可不动 |
| **V2** | **Stone Web Viewer**（Orthanc 插件） | 装 Stone 插件，从 Orthanc 打开检查 | **少一套独立前端**；和 A1 同进程生态；部署清单短 | 工具深度、挂片、社区工作流弱于 OHIF；阅片绑 Orthanc | 换归档通常要**连阅片一起换** |
| **V3** | **Weasis** | DICOMweb/WADO 拉 Orthanc | 桌面功能全（窗宽、3D 等） | 要装客户端；「Web 阅片」口径弱，C7 需院方书面认 | 客户端协议要重配 |
| **V4** | **商业 Web Viewer** | 厂商认 DICOMweb 则指 Orthanc；否则可能要求换他们的归档 | 医生体验、售后由厂商扛；ZXPlat 只留 URL 模板 | **国基目前无合同**；不少商业阅片捆绑自家 VNA，和 A1 打架 | 看合同是否锁归档 |

**不要把这两样当成 V2**

| 名称 | 实际是什么 | 归类 |
|------|------------|------|
| Orthanc Explorer 2 | 管理界面，能点开图，**不是**诊断级阅片 | 不能单独当 F2 |
| Orthanc 的 OHIF 插件 | 仍是 OHIF，只是塞进 Orthanc 进程 | 仍是 **V1**，只是部署方式更省一个容器 |

**和 C7、ZXPlat 工作量的关系（F1=A1 已定）**

| | V1 OHIF | V2 Stone | V3 Weasis | V4 商业 |
|--|---------|----------|-----------|---------|
| 过「DICOM Web 阅片」 | ✅ 浏览器 | ✅ 浏览器（能力偏基础） | ⚠️ 要确认 | ✅（有产品时） |
| ZXPlat 要做的 | URL+Token+反代鉴权 | URL+Token（更短） | 启动协议/安装说明 | URL 模板 |
| 首版联调风险 | 中（两组件对版本） | 低（同厂商插件） | 中（客户端环境） | 高（无合同则停） |
| 多院区一院一 Orthanc（E3） | 每节点一套 OHIF 配置，或一个 OHIF 按院区切数据源 | 阅片跟节点走，跨院要跳不同 URL | 客户端配多个节点 | 按厂商路由 |

**本项参考（非强制）**：无采购、要浏览器诊断阅片、且以后可能换归档 → **V1**。运维只想多一个 Orthanc 插件、接受功能偏基础 → **V2**。

#### V1 与 V2 的功能差、中文（F1=A1 已定）

> 依据：OHIF 文档（i18n、`?lng=zh`）与 Orthanc Book（Stone 快速入门、FAQ、TODO；Stone 3.0 发布说明，2025-12）。两边默认都**不是**注册医疗器械。

**日常 2D 看图，两边都有**：翻页、窗宽窗位（含 CT 预设）、缩放平移、多视口对比序列、基础标注、截图/导出。国基若主要是 DR/超声/普通 CT 浏览写报告，**功能够用上 V2 能过**。

**V1 有、V2 官方仍列为未交付或明显弱的**：

| 能力 | V1 OHIF v3 | V2 Stone |
|------|------------|----------|
| MPR / MIP / 体绘制 | 已有 | 官方列为**未来项**（要赞助才做） |
| PET/CT 融合、RT Dose/勾画 | 近期版本已有 | 未作为现成能力 |
| 测量种类与跟踪 | 长度、角度、ROI、箭头等，可跟踪/导出 | 有标注工具；**把标注存回检查**仍在 TODO |
| 挂片布局 | 多格、可配工作流 | 以双视口对比为主，布局简单 |
| 界面中文 | **内置 `zh`**，URL `?lng=zh` 或偏好里切换；词条不全时回退英文 | **没有成品 i18n**；官方 TODO 仍写 internationalization；界面文案为英文 |
| 影像里的中文姓名/描述 | 浏览器字体；DICOM 字符集正确即可显示 | 侧栏是网页文本，字符集正确一般能显示中文；**按钮和菜单仍是英文** |
| 定位 | 可扩展的临床向 Web 工作站 | 官方定位：**2D 远程阅片、省带宽、快** |
| 和归档的耦合 | 走 DICOMweb，可换归档 | 插件绑 Orthanc；视频播放还走 Orthanc 私有 REST |

**中文结论**：要给医生中文按钮和菜单，选 **V1**（可再补缺词）。选 **V2** 则界面保持英文，只能保证影像标签里的中文姓名在字符集正确时能看见。

→ **国基已选定 F2=V1 OHIF Viewer v3**（2026-09-21）。启动 URL 带 `lng=zh`；缺词回退英文，可在 `@ohif/i18n` 补。取图走 Orthanc DICOMweb，不把 OHIF 渲染写进 ZXPlat。

### 0.5 F3 · 关键图存储组件（选且仅选一项）

| 代号 | 组件/方式 | 是什么 | 利 | 弊 | 依赖 |
|------|-----------|--------|----|----|------|
| **K1** | **本地/NAS + Media 索引** | 落盘，DB 存路径 | 最快；不绑归档；像遗留 savePic | 多节点要共享盘；备份另策 | 无 |
| **K2** | **与报告 PDF 同一文件服务** | 复用 ZXPlat 已有存储 | 运维统一；权限可复用 | 依赖现有存储是否就绪 | ZXPlat 文件服务已上线 |
| **K3** | **Orthanc 附件/派生图** | 关键图进 Orthanc | 与 DICOM 同库 | API 与普通文件不同 | **F1=A1 或 A2** |
| **K4** | **MinIO 独立桶** | key-images bucket | 扩展与生命周期清晰 | 多一套组件 | MinIO 运维 |
| **K5** | **不持久** | 临时图 | — | **不过 C7** | — |

**禁止定稿**：K5。  
**前提**：F1=A1、F2=V1 已锁。关键图是给**报告嵌图**用的 JPEG/PNG，不是 OHIF 里的 DICOM 序列。ZXPlat 报告目前只存 `pdfStorageKey` 字符串，仓库里**尚无** MinIO/S3 客户端。

#### 在 F1=A1、F2=V1 下，F3 怎么比

| 代号 | 存在哪 | 利 | 弊 | 和 OHIF 的关系 | 和现有 PDF 的关系 |
|------|--------|----|----|----------------|-------------------|
| **K1** | imaging 服务器本地盘或 NAS；`Media` 表存路径 | 不依赖新中间件；和遗留 `savePic` 一样；报告用 HTTP 取图即可；不把截图塞进 DICOM 库 | 应用多实例时要共享盘；备份要单独做，和 Orthanc 卷不是一处 | OHIF **不**显示这些图；报告页单独画廊 | 与 PDF 分开 |
| **K2** | 与报告 PDF 同一套文件服务 | 权限、备份、预览可以和 PDF 走一条管道 | **文件服务还没落地**（只有键，没有存储实现）；选 K2 等于先做或等待统一对象存储 | 同上，报告页取 URL | 理论上统一；实现上要先有存储 |
| **K3** | Orthanc 附件（挂在 Study/Instance 上） | 和 DICOM **同一块盘、同一次备份**；F1 已是 Orthanc，不再加组件 | 附件 API 与普通文件不同；JPEG 附件**不会**自动出现在 OHIF 序列里，除非再转成 Secondary Capture 再入库；换归档（E5）时关键图要一起迁 | 默认仍是报告页取图；要在阅片里看到，得多一步 DICOM 封装 | 与 PDF 分开 |
| **K4** | 单独 MinIO 桶 | 生命周期、扩容、预签名 URL 清晰 | 全仓库还没用 MinIO，等于为关键图**新上一套**对象存储；运维和权限都要新做 | 报告页用预签名 URL | 除非同时把 PDF 也迁进 MinIO，否则仍是两套 |

**过 C7「关键图」**：K1～K4 都能过，只要报告能按 `Media` 列出并打开图片。差别在运维和要不要进 OHIF。

**本项参考（非强制）**：首版只在报告里嵌图、单机部署 → **K1**。希望和 DICOM 同卷备份、接受 OHIF 里默认看不到截图 → **K3**。已决定全院文件走对象存储（含 PDF）→ 再选 **K2 或 K4**，见下。

#### K2 与 K4（只比这两项）

K2 定的是**和 PDF 共用同一套存储**；K4 定的是**现在就上 MinIO，且关键图单独一桶**。今天 PDF 只有 `pdfStorageKey`，字节存储未实现，所以两者都还没有现成服务可接。

| | **K2 同 PDF 文件服务** | **K4 独立 MinIO 桶** |
|--|------------------------|----------------------|
| 现在要做什么 | 等或先做「PDF 用的那套存储」，关键图跟着进 | 为关键图单独部署 MinIO；PDF 仍只有键 |
| 组件数 | 不新增产品名；存储产品以后和 PDF 一起定 | 明确多一个 MinIO |
| 备份与权限 | 和 PDF 同一处、同一套账号 | 关键图自己一套；PDF 另说 |
| 保留策略 | 跟病历 PDF 绑在一起，不好单独给图片设过期 | 桶上可单独设生命周期（图比 PDF 大、保留期可以不同） |
| 故障 | PDF 和图一起不可用 | 图挂了不影响 PDF 键；但 PDF 下载本来也还没做 |
| 以后 PDF 也上 MinIO | 自然变成「同一个 MinIO，同一桶或同一前缀」 | 仍是同一集群里的**另一个桶**，只是比 K2 更早把 MinIO 引进来 |

若最终存储就是 MinIO：K2 = PDF 与关键图一起上；K4 = 先只让关键图上 MinIO。差别是**开工时间和是否与 PDF 同桶**，不是两套互斥产品。

→ **国基已选定 F3=K4**（2026-09-21）。关键图进 MinIO 独立桶（建议桶名 `key-images`）；`Media` 存对象键；报告用预签名 URL 嵌图。PDF 仍只保留 `pdfStorageKey`，不进该桶。以后 PDF 若上 MinIO，用同集群的另一桶，不并进关键图桶。

### 0.6.1 取图协议（待拍；在 F1=A1、F2=V1 下解释）

本项只决定 **OHIF 如何向 Orthanc 要 DICOM 像素**。另外两条路不在本项里：

| 数据 | 怎么走 | 是否本项 |
|------|--------|----------|
| 设备把图送进归档 | DICOM **C-STORE** → Orthanc 4242 | 否（入库） |
| 报告里的关键图 | HTTP 预签名 → MinIO `key-images` | 否（F3=K4） |
| 浏览器阅片拉序列/帧 | **本项** | 是 |

| 选项 | 阅片实际怎么取 | 利 | 弊 |
|------|----------------|----|----|
| **DICOMweb** | OHIF 配 `qidoRoot`/`wadoRoot`。**QIDO-RS** 查 Study/Series；**WADO-RS** 取帧。可选 **STOW-RS** 做手工 DCM 上传（与 C-STORE 并列，不替代设备入库） | 和已定的 OHIF 默认数据源一致；以后换归档（E5）只改 URL；ZXPlat 不实现协议，只做反代鉴权 | 要开 Orthanc DICOMweb 插件；管理接口不能对浏览器裸奔 |
| **厂商私有** | 走 Orthanc 自己的 REST（`/instances/.../frames`），或将来某商业 PACS 的私有 API | 有的接口比 DICOMweb 少一次查询 | OHIF **不能直接用** Orthanc REST，要自写数据源；阅片绑死 Orthanc，E5 要重做；国基没有商业私有 API 可接 |
| **混合** | 阅片仍是 DICOMweb，另允许 adapter 调 Orthanc REST 做入库通知、删图、查磁盘等 | 管理动作不必硬塞进 DICOMweb | 两条调用要写清边界，否则业务代码会偷偷依赖私有 API |

**和「adapter 能否调 Orthanc REST」的差别**：选 DICOMweb 只锁**阅片取像素**。入库回写、健康检查仍可以在 adapter 内部调 Orthanc REST，只要 Domain 不把这些 URL 当成取图协议。那不叫「混合取图」。

**在已定组件下**：OHIF 的取图路径就是 DICOMweb。选「厂商私有」等于放弃现成 OHIF 数据源。选「混合」若指阅片也走私有接口，和 F2 冲突；若只指管理口可走 REST，不需要把取图协议定成混合。

→ **国基已选定取图协议=DICOMweb**（2026-09-21）。OHIF 用 QIDO-RS 查、WADO-RS 取帧；ZXPlat 只做反代鉴权。adapter 内部仍可调 Orthanc REST 做入库回写，不把 REST 当作阅片取图协议。

#### 三条数据各在哪（定稿后对照）

| 数据 | 协议 | 落点 | 文档位置 | 谁消费 |
|------|------|------|----------|--------|
| **设备入库** | DICOM **C-STORE**（端口示例 4242） | **Orthanc** 存 DICOM；ZXPlat 写 `ImagingStudy`、回写 StudyUID | 本表；CAP-10；工作顺序 **序号 58** | 设备 → Orthanc；不经 OHIF |
| **阅片取图** | **DICOMweb** QIDO-RS / WADO-RS | Orthanc DICOMweb 插件 → **OHIF** | 本项（取图协议） | 浏览器 OHIF |
| **关键图** | HTTP 预签名 | **MinIO 桶 `key-images`**；`Media` 存对象键 | **F3=K4**（§0.5） | 报告页嵌图；**不进 OHIF 序列** |

## 一、选型原则

| 原则 | 说明 |
|------|------|
| **不重写 Viewer** | 窗宽窗位、MPR、测量、挂片等人年级工作量，ZXPlat 不做 |
| **标准接口优先** | 归档与阅片之间优先 **DICOMweb** |
| **分层解耦** | **归档** ≠ **显示** ≠ **RIS**，可独立替换 |
| **院点可替换** | 商业 Viewer 时仅配 URL 模板（F2=V4） |
| **与遗留一致** | `goCheckWpacs` 本质是 **URL + Token**，非自研渲染 |

**ZXPlat 自建范围**：采集编排、`ImagingStudy`/`Media`、`hasMedia` 回写、阅片 Token/URL、可选 DICOMweb 鉴权网关。
