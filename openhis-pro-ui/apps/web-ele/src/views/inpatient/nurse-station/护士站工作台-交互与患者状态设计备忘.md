# 护士站工作台：交互与患者状态设计备忘

> **定位**：在纯前端布局之后、接口与详细交互定稿之前，用于收敛难点、预留扩展点与待决策项。  
> **非契约**：本文不绑定具体接口路径与字段名；实现时可随产品结论修订。

---

## 1. 文档目的与范围

| 项           | 说明                                                                            |
| ------------ | ------------------------------------------------------------------------------- |
| **目的**     | 提前识别「右侧多 Tab 共用左侧患者列」场景下的交互与状态风险，避免后期推翻壳层。 |
| **范围**     | 护士站工作台：左侧患者列表（筛选、选择）+ 右侧业务 Tab 内容区。                 |
| **不在范围** | 具体 UI 像素、组件库选型、后端表结构。                                          |

**核心约束（产品层）**

- 左侧患者列表为**全站该工作台内**患者上下文的**主展示面**；右侧各 Tab 共享同一套患者数据视图，但可对「筛选默认值、选择模式、数据投影」有不同策略。
- **单一事实源（SSOT）**：以工作台层维护的患者主数据为准；子模块使用只读投影，不私自作为主数据源写入冲突结构。

---

## 2. 信息架构与状态分层

建议在心里（或代码注释里）固定下列分层，避免「筛选、选中、Tab」三者逻辑缠绕。

```
┌─────────────────────────────────────────────────────────────┐
│ L0 患者全集 / 缓存（可分页、可按病区增量加载）                 │
├─────────────────────────────────────────────────────────────┤
│ L1 空间与检索范围：病区、病房、关键字、时间窗（可选）          │
├─────────────────────────────────────────────────────────────┤
│ L2 临床/任务维度筛选：待校对、待执行、已处理等（可扩展谓词）    │
├─────────────────────────────────────────────────────────────┤
│ L3 选择集：单选 / 多选 / 空（与 L2 可解耦）                   │
├─────────────────────────────────────────────────────────────┤
│ L4 当前 Tab 策略：进入默认筛选、是否锁定、右侧模块 id         │
└─────────────────────────────────────────────────────────────┘
```

**与床位图的关系**：床位图往往依赖 **L1 下某病区/病房的「床位列 + 在院患者」**，可能与 **L0 列表分页** 的数据范围不一致，属于常见难点，见第 4.2 节。

## 3. 交互难点细化

### 3.1 Tab 切换与筛选的耦合

**现象**

- 进入「医嘱校对」时期望列表默认只显示「有待校对任务」的患者；进入「医嘱执行」同理。
- 用户已在左侧手动改为「全部状态」，再切换 Tab：是否被 Tab 再次覆盖？

**需提前决策的维度**

| 决策点 | 选项 A | 选项 B | 选项 C |
| --- | --- | --- | --- |
| Tab 对筛选的影响 | 每次进入 Tab 强制应用预设 | 仅首次进入该 Tab 应用，之后用户优先 | Tab 内锁定筛选，离开前不可改 |
| 离开 Tab 后 | 恢复离开前全局筛选 | 保留 Tab 留下的筛选 | 每次回工作台首页重置 |

**预留**

- Tab 元数据占位：`defaultFilterPresetId`、`filterBehaviorOnEnter: 'force' | 'once' | 'none'`。
- 统一入口：`onWorkbenchTabChange(tabId, prevTabId)`，所有「因 Tab 导致的筛选变更」只从这里触发，便于埋点与单测。

---

### 3.2 单选 / 多选随场景变化

**现象**

- 批量医嘱执行需要多选；某些核对或单患者文书可能只要单选；入出转、点床场景常等价于「当前操作患者」唯一。

**需提前决策**

| 决策点       | 说明                                                             |
| ------------ | ---------------------------------------------------------------- |
| 选择模式来源 | 按 Tab 固定，还是按「当前子流程」（例如弹窗内批量）临时切换？    |
| 模式切换瞬间 | 从多选切到单选：保留「第一个选中」、保留「主上下文」、还是清空？ |
| UI 一致性    | 单选时是否隐藏复选框、卡片点击是否等价于 radio？                 |

**预留**

- `selectionPolicy: 'single' | 'multiple' | 'none'`（`none`：仅浏览，不强调选中）。
- `normalizeSelectionAfterPolicyChange(policy)`：集中实现收敛规则，禁止在多个 `@click` 里复制粘贴。

---

### 3.3 选中患者与当前列表筛选「不一致」

**现象**

- 筛选收紧后，已选中患者不在 `filteredList` 中；右侧模块仍可能展示该患者详情，造成「列表里看不到选中的人」。

**需提前决策**

| 策略 | 适用 |
| --- | --- |
| **严格** | 筛选变化时剔除不在范围内的选中。 |
| **宽松** | 保留选中；列表顶部提示「当前筛选不包含已选患者」，提供「跳转到该患者」或「清除筛选」。 |
| **上下文独立** | 引入 `contextPatientId`（或少量 id）与「列表筛选集合」分离，右侧只认 context。 |

**预留**

- 区分命名：`filteredPatientIds` / `selectedPatientIds` / `contextPatientId`（是否合并由产品定）。
- `syncSelectionWithFilter(filterChangeReason)` 单点处理。

---

### 3.4 左侧列表与床位图 / 其他视图的选主冲突

**现象**

- 列表点击、卡片多选、床位图点床、拖放完成，多个入口都会改「当前患者」。

**需提前决策**

- 是否区分 **「主操作患者」**（右侧大面板）与 **「批量选中集」**（列表勾选）：二者是否允许并存。

**预留**

- `setActivePatient(patientId, source: 'list' | 'bed' | 'tab' | 'system')`：所有入口汇总；`source` 便于埋点与不同合并策略。

---

### 3.5 批量操作与部分失败

**现象**

- 对 5 名患者执行动作，部分成功部分失败；是否自动取消成功项的选中、失败项保留？

**预留**

- 结果结构占位：`(patientId, ok, errorCode?)[]`。
- UI 占位：底部或顶部「操作结果条」、可重试列表；不必布局期实现逻辑。

---

### 3.6 数据新鲜度与长时间停留

**现象**

- 页面开很久，他处已变更医嘱状态或办理出院，列表仍显示旧态。

**预留**

- `refreshPatients(reason: 'manual' | 'interval' | 'push' | 'focus')`。
- `subscribePatientUpdates()` / `unsubscribePatientUpdates()`（WebSocket 或 SSE 时接入）。

---

### 3.7 Tab 权限与深链

**现象**

- 用户无某 Tab 权限时隐藏入口；URL 仍带该 `tabId` 时的降级（跳到第一个可用 Tab + 可选提示）。

**预留**

- `resolveTab(tabId): TabId | null` 与 `getDefaultTabForUser()`。

---

### 3.8 键盘与无障碍（若产品要求）

**现象**

- 列表 roving tabindex 与表格内编辑、与全局快捷键冲突。

**预留**

- 列表根节点统一 `data-workbench-patient-list` 或单一 `ref`，便于后续挂键盘导航而不打散在各卡片。

---

## 4. 患者状态管理难点细化

### 4.1 单一事实源与只读投影

**现象**

- 子模块各自 `ref` 复制患者列表，导致 PATCH 后不同步。

**原则**

- 工作台层（layout / store / composable）持有 SSOT。
- 子模块通过 `getPatientById`、`listPatientsProjection(scope, moduleId)` 获取只读数据；写操作经 `applyPatientPatch` 或领域命令封装。

**预留**

- 注释或类型：`PatientProjectionForAudit`、`PatientProjectionForBedMap` 等，避免一个巨型 `Patient` 强迫所有 Tab 相同字段。

---

### 4.2 列表分页与床位图数据范围

**现象**

- 列表接口分页；床位图需要「本病区固定床网 + 占床患者 + 未分床在院患者」，范围更大或不同接口。

**预留**

- 概念拆分：`listQueryScope`（列表）与 `wardBoardScope`（床位图）；文档中记录「允许两个请求合成一屏」即可。

---

### 4.3 乐观更新与回滚

**现象**

- 分床、换床先动 UI，请求失败需还原。

**预留**

- `beginPatientMutation(meta) → mutationId` / `commitPatientMutation(mutationId)` / `rollbackPatientMutation(mutationId)`，或简化为 `applyLocalPatch` + `revertPatch(patchId)` 占位。

---

### 4.4 刷新与持久化

**现象**

- F5 后是否恢复选中、当前 Tab、筛选？

**预留**

- 可选策略位：`persistSelection: boolean`、`persistTab: boolean`、存储介质 `sessionStorage | urlQuery`（实现延后）。

---

### 4.5 筛选谓词与后端演进

**现象**

- 「待校对」最初是患者聚合字段；后期可能变为子资源计数或独立查询，前端枚举不够。

**预留**

- 筛选用 `FilterDescriptor { key: string; params?: Record<string, unknown> }` 或后端返回的 `filterToken`，避免 UI 写死四个枚举贯穿全仓。

---

### 4.6 并发与版本冲突

**现象**

- 多终端同时操作；本地列表与服务器版本不一致。

**预留**

- 患者对象预留 `version` 或 `updatedAt`；冲突回调 `onPatientConflict(patientId, detail)`。

---

### 4.7 出院 / 转科 / 移出本病区

**现象**

- 当前选中患者不再属于工作台范围，右侧需关面板、清空或自动切到下一患者。

**预留**

- `onPatientRemovedFromScope(patientId, reason: 'discharge' | 'transfer' | 'scopeChange')`。

---

## 5. 建议预留的 API / 钩子（实现可空壳）

下列名称仅为建议，实现时可改为 composable 或 store actions。

| 名称 | 职责 |
| --- | --- |
| `onWorkbenchTabChange(tabId, prevTabId)` | Tab 切换：应用默认筛选、选择策略、必要时 `normalizeSelection`。 |
| `setSelectionPolicy(policy)` | 设置单/多/无选择；与 UI 展示联动。 |
| `normalizeSelection()` | 策略或筛选变化后收敛选中集合。 |
| `setActivePatient(patientId, source)` | 统一「当前主患者」入口。 |
| `setPatientFilter(descriptor \| presetId)` | 与 Tab 解耦的筛选设置入口。 |
| `syncSelectionWithFilter(reason)` | 筛选变化后与选中集对齐（按产品选严格/宽松）。 |
| `refreshPatients(reason)` | 手动 / 定时 / 推送 / 窗口聚焦刷新。 |
| `getPatientProjection(patientId, moduleId)` | 右侧模块差异化字段。 |
| `onPatientScopeOrDataChanged()` | 通知子模块刷新（事件、provide/inject 或 store）。 |
| `resolveTab(tabId)` | 权限降级与默认 Tab。 |
| `onPatientRemovedFromScope(patientId, reason)` | 出院、转科、范围变更。 |
| `onPatientConflict(patientId, detail)` | 版本冲突处理。 |

---

## 6. 与后端 / 产品需对齐的清单（占位）

- [ ] 列表是否分页；排序规则；默认病区是否来自登录科室。
- [ ] 「待校对 / 待执行」是患者级聚合还是独立查询接口。
- [ ] 床位图数据是否与列表同接口、分字段还是分接口。
- [ ] 写操作（分床、执行、校对）是否统一幂等与错误码表。
- [ ] 是否需要实时推送；推送粒度（患者级 / 病区级）。
- [ ] 选中与上下文是否需写入 URL（便于分享、刷新恢复）。

## 7. 实施优先级建议

| 优先级 | 内容 |
| --- | --- |
| P0 | `onWorkbenchTabChange` + `setActivePatient` + `selectionPolicy` + `normalizeSelection` 四条线各单一入口。 |
| P1 | `filtered` 与 `selected` / `context` 不一致时的产品策略 + `syncSelectionWithFilter`。 |
| P2 | `listQueryScope` 与 `wardBoardScope` 数据策略；`refreshPatients` 与推送占位。 |
| P3 | 乐观更新与冲突、`persistSelection`、键盘无障碍。 |
